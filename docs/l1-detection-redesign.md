# L1 試合境界検出アプローチ再設計

## 背景

L1 の目的は FL 長時間録画を試合単位に分割すること。現行アプローチ（輝度検出 + scorebar ROI 分類 + 音声 BGM 相関。#284 で L1 スコープ内に統合承認済み）は境界検出精度に構造的限界があり、L1 必達要件である「試合の切れ目を正確に検知して動画を分割する」が実現できない可能性があると判断した。

本ドキュメントは現行アプローチの問題点を整理し、ゼロベース再設計の選択肢と採用方針を記録する。

## 現行アプローチが行き詰まっている構造的要因

1. **信号が本質的に曖昧** — 輝度・scorebar ROI・音声 BGM いずれも単独では境界と非境界を分離しきれない。特に scorebar は試合終了後 0-60s の残像で試合中と視覚的に識別不能（#271 で engineer-1 が実証）
2. **ヒューリスティック層の複合化** — 閾値・判定ロジックを層ごとに積み上げる設計が、ある層の edge case 修正で別の層に副作用を生む連鎖を生じさせている
3. **ground truth の欠如** — 各候補が真か偽かの判定を都度ユーザー確認に依存（#286 で 5 候補中 2 件が真、3 件が偽と判明）。自動化率を上げるほど誤検出も増えるジレンマ
4. **スコープ肥大** — L1 の目的は「分割」のはずが、実質的に「試合を文脈的に理解する」タスクになっている

## 検討した代替アプローチ

### A. UI 要素ベースの状態機械方式【採用】

FL 画面は明確な UI ステート（ロビー → カウントダウン → HUD タイマー表示中の試合中 → リザルト画面 → ロビー）を持つ。各ステートに対応する **決定的な UI 要素**（HUD タイマー、スコアボード、"試合開始まで" 文字列、リザルト画面特有のレイアウト等）を、OCR またはテンプレートマッチで検出する。

- フレームサンプリング → ステートラベリング → FSM で状態遷移 → 遷移点が試合境界
- 輝度や ROI 平均のような曖昧な特徴ではなく、UI 要素の「あり/なし」の二値判定が中心となる
- 依存: OpenCV テンプレートマッチング（軽量）+ 限定的 OCR

**採用理由**:
- 現行アプローチの根本問題（曖昧信号の積み上げ）を回避できる
- 各フレーム判定が明確で、偽陽性の原因追跡が容易
- FF14 UI の公開画面要素を対象とするため、法的懸念（音声派生データ配布）も発生しない
- 同期段階で他アプローチよりも設計の単純性が高い

**既知の懸念**:
- FF14 UI パッチで UI 要素が変更された場合、テンプレート/OCR 領域の更新が必要
- ユーザー環境の UI スケール・HUD レイアウト設定による検出ぶれ

### B. FFXIV ゲームログ連携方式【現時点で不可、将来再検討】

FFXIV クライアントのチャットログ/コンテンツログから PvP コンテンツ入退場イベントを取得し、録画タイムスタンプと相関して境界を確定する。

**現時点で採用しない理由**:
- ユーザー方針として「動画データ以外（ログファイル等）の採取は現時点で不可」
- ログ形式の非公開性、ACT / XIVLauncher 等の外部プラグイン前提になる可能性

**将来再検討のトリガー**:
- A アプローチが FF14 UI パッチ更新に繰り返し破綻し、保守コストが過大になった場合
- ユーザー側でログデータの採取・連携が可能になった場合
- ゲームログ API / プラグインが公式に整備された場合

### C. 対話的確認方式【L2 GUI サポートで採用】

自動検出を「候補提示」に留め、ユーザーが GUI 上で承認/却下して最終境界を確定する。

L1 の CLI 基盤では導入せず、**L2（GUI サポート）のスコープで採用する**。L1 が A アプローチで高精度を実現できていれば、L2 では「低信頼度境界のみユーザー確認」「確認結果のフィードバックで閾値を学習」等の UX 拡張として位置づける。

**設計案（L2 での実装時に参照）**:
- L1 で検出した境界候補を信頼度スコア付きで出力
- GUI 側で候補ごとに ±10 秒程度のプレビュー画像/動画サムネイルを表示
- ユーザーは承認/却下/境界位置の微調整を行える
- 承認/却下のフィードバックをログとして保存し、A アプローチの閾値チューニング・テンプレート追加の教師データとする
- 低信頼度 tier（例: FSM 遷移が曖昧、複数候補が競合）のみユーザー確認を要求し、高信頼度は自動採用する段階的運用

**L2 採用時の前提**:
- L1 で A アプローチが安定稼働していること（L1 の精度が低いと確認対象が多すぎて UX が破綻）
- L2 の GUI 技術選定（Electron / Tauri / Web ベース / ネイティブ）が決定済みであること

### D. 軽量 ML 分類器方式【最終手段として温存】

フレーム状態（in_match / lobby / loading / result_screen 等）を scikit-learn 等の軽量モデルで学習し、フレーム単位で分類する。

**現時点で採用しない理由**:
- A および B の双方が行き詰まった場合の最終手段として温存
- 現在 4 録画の教師データでは学習量が不足
- 閾値調整の自動化は魅力的だが、解釈性・デバッグ性が落ちる

**設計案（最終手段として採用する場合の参照）**:
- 特徴量候補: ダウンサンプルフレーム（例 64x36 grayscale / カラー）、輝度ヒストグラム、ROI ごとの統計量、エッジ密度、scorebar 領域の特徴、時系列差分
- モデル候補: 軽量順に logistic regression / random forest / gradient boosting / small CNN
- ラベル: 手動アノテーション。C の対話的確認ログが蓄積されていればそれを教師データ流用
- L1 ランタイムで推論する場合、モデル同梱（数 KB〜数 MB）+ scikit-learn 依存追加で済む
- 評価: 録画単位 k-fold、境界時刻精度（±N 秒以内の検出率）と偽陽性率

**採用判断のトリガー**:
- A アプローチが UI パッチ追従コスト高で破綻
- B も不可の状態が継続
- C の対話ログが十分に蓄積され教師データ化できる
- 上記を満たした時点で D の PoC を実施し、精度が A を上回るなら切替

## 採用範囲と廃棄範囲

### 継続利用するモジュール

- CLI 基盤（`cli.py`, `commands/`）
- `ffmpeg_path.py`, `video/probe.py`, `video/splitter.py`
- `config.py`, `exceptions.py`
- 運用ドキュメント（`docs/release-strategy.md`, `docs/roles/*`, `docs/issue-policy.md`, `docs/guard-integration.md` 等）

### 廃棄・再設計するモジュール

- `video/detector.py`（輝度検出・Pass 1/2・transition expansion）
- `video/scorebar.py`（scorebar ROI 分類）
- `video/gpu_detector.py`（GPU モード実装）
- `commands/debug_brightness.py`（A アプローチ採用で有用性大幅低下）
- #284 で承認した音声 BGM L1 統合（`allaganeye/audio/` 追加、参照特徴量同梱）は **実装着手前のため即時取り下げ**

既存テスト（`tests/test_detector.py` 等）も対応モジュール廃棄に伴い再設計対象。

1. **lead-1 への A アプローチ技術評価依頼**（新規 `[question]` issue）
