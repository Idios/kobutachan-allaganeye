# L1 試合境界検出アプローチ再設計

## 背景

L1 の目的は FL 長時間録画を試合単位に分割すること。現行アプローチ（輝度検出 + scorebar ROI 分類）は暗転検知自体の精度は高い（7/7 試合検出）が、暗転前後の **分類精度** に構造的限界がある。音声 BGM 検出（#287/#288 で実装・マージ済み）も Fanfare 単独では偽陽性の分離が困難であることが判明した。

本ドキュメントはこれらの限界を整理し、**暗転検知 + FL UI 検出 + 音声補助の複合判定**への進化方針を記録する。

## 現行アプローチの構造的限界

### 暗転検知（維持）

暗転検知自体は安定している。Pass 1 粗いスキャン → transition expansion → Pass 2 精密計測のパイプラインは今後も中核信号として維持する。

### scorebar ROI 分類の限界

1. **scorebar 残像問題** — 試合終了後 0-60s の残像で試合中と視覚的に識別不能（#271 で engineer-1 が実証）
2. **ROI 平均値の曖昧さ** — `_has_scorebar` がロビー UI の鮮やかな背景（ch_std > 閾値）で偽陽性を多発。チューニングでは対応不能（#303 ユーザー実視聴確認済み）
3. **ヒューリスティック層の複合化** — 閾値・判定ロジックを層ごとに積み上げる設計が、ある層の edge case 修正で別の層に副作用を生む連鎖を生じさせている

### 音声 BGM 検出の限界（実装済み・凍結）

- Fanfare 検出は #271 問題 2（57:53 隠れ試合終了）を解決（PR #302）
- しかし Fanfare 単独では noise/real の sim overlap (0.668-0.976) で分離不能（#303 検証済み）
- `allaganeye/audio/` モジュールはマージ済みのためコードを保持し、将来の複合判定での再統合に備えて凍結する

## 採用する方式: 暗転検知 + FL UI 検出 + 音声補助

「全面置換」ではなく、既存の暗転検知を主信号として維持しつつ、暗転前後の分類を FL UI 検出で刷新する。

| 信号 | 役割 | 方式 | モジュール |
|---|---|---|---|
| 暗転検知 | 主信号。試合境界候補の収集 | 既存 Pass 1/2 を維持 | `video/detector.py`, `video/gpu_detector.py` |
| FL UI 検出 | 暗転前後の分類。scorebar → テンプレートマッチ化 + 自己キャリブレーション | 新規実装（既存モジュール改修） | `video/scorebar.py` → 刷新 |
| 音声 | 補助。暗転 + UI で曖昧な場合のみ | 既存 `audio/` を凍結、将来再統合 | `audio/`（凍結） |

### FL UI 検出の設計方針

FL 中のみ表示される UI 要素を検出し、暗転前後のフレームが「FL 試合中」か否かを判定する。

**判定利用可能な FL 固有 UI:**

| UI 要素 | 位置固定 | スケール可変 | 非表示設定 |
|---|---|---|---|
| scorebar | **固定** | 固定 | 不可 |
| ゲームタイマー | 可 | 可 | 可 |
| アドレナリンラッシュゲージ | 可 | 可 | 可 |
| 高揚ゲージ | 可 | 可 | 可 |

**自己キャリブレーション方式:**

scorebar 以外の UI はユーザーの HUD レイアウト設定で位置・サイズが異なるため、固定テンプレートでは対応できない。録画セッション単位で自動的にプロファイルを学習する:

1. **アンカー検出**: scorebar（固定位置）の出現で FL 試合開始を確定
2. **プロファイル学習**: 開始直後の安定フレームで可動 UI（タイマー / アドレナリン / 高揚）の現在位置・サイズを発見し、録画セッション用の ROI として記憶
3. **範囲判定**: 以降は記憶したプロファイルで各 UI の有無を追跡し、UI 消失 → 試合終了とする
4. **前提**: 1 録画 = 1 HUD 設定（OBS 録画中に HUD を編集するケースは稀）

**現行 ROI 平均値方式との違い:**

- ROI 内のチャンネル標準偏差（連続値の閾値判定）→ テンプレートマッチング（二値判定）
- 固定位置前提 → 自己キャリブレーションで環境依存を構造的に解消
- scorebar 1 本の判定 → 複数 UI の併用で偽陽性耐性向上

**技術評価の依頼先:** #293（A 案技術評価、`role:lead-engineer`、P1-high）で lead-1 が評価中。director-1 の自己キャリブレーション設計入力もコメント済み。

### 全フレーム走査 FSM（不採用）

当初検討した「全フレームをサンプリング → FSM で状態遷移を追跡」方式は、暗転検知と重複するコストが大きく、L1 の処理時間を大幅に増加させる。暗転前後のフレームのみを FL UI 検出する複合判定方式の方が効率的であり、既存アーキテクチャとの親和性も高い。

## 検討したが不採用のアプローチ

### B. FFXIV ゲームログ連携方式【現時点で不可、将来再検討】

FFXIV クライアントのチャットログ/コンテンツログから PvP コンテンツ入退場イベントを取得し、録画タイムスタンプと相関して境界を確定する。

**現時点で採用しない理由**:
- ユーザー方針として「動画データ以外（ログファイル等）の採取は現時点で不可」
- ログ形式の非公開性、ACT / XIVLauncher 等の外部プラグイン前提になる可能性

**将来再検討のトリガー**:
- FL UI 検出が FF14 UI パッチ更新に繰り返し破綻し、保守コストが過大になった場合
- ユーザー側でログデータの採取・連携が可能になった場合

### C. 対話的確認方式【L2 GUI サポートで採用】

自動検出を「候補提示」に留め、ユーザーが GUI 上で承認/却下して最終境界を確定する。

L1 の CLI 基盤では導入せず、**L2（GUI サポート）のスコープで採用する**。L1 が高精度を実現できていれば、L2 では「低信頼度境界のみユーザー確認」等の UX 拡張として位置づける。

### D. 軽量 ML 分類器方式【最終手段として温存】

フレーム状態を scikit-learn 等の軽量モデルで学習し分類する。

**現時点で採用しない理由**:
- FL UI 検出および B の双方が行き詰まった場合の最終手段として温存
- 教師データの蓄積が不足（4 録画）
- 解釈性・デバッグ性が落ちる
