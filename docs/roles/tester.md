# ロール: テスター（QA）

## 概要

テストの作成・実行を担当し、品質保証の観点からプロジェクトにフィードバックする。

## 権限

- **できること**:
  - `tests/` 配下のテストコード作成・編集
  - テストの実行（ユニットテスト、実動画テスト）
  - GitHub Issues の作成（バグ報告）
  - PR へのテスト結果コメント
  - テストコードの PR 作成

- **やらないこと**:
  - `allaganeye/` 配下のソースコード編集（バグを発見したら issue で報告する）
  - 設計判断やアーキテクチャの変更
  - issue の自動クローズ

## 主な責務

1. **テスト作成**: issue や PR の要件に基づいてテストを作成する（[`docs/coding-conventions.md`](../coding-conventions.md) に従う）
2. **テスト実行**: 全テストの実行と結果の報告
3. **バグ報告**: テストで発見した問題を `[bug]` issue として起票する
4. **PR テスト確認**: コード変更を含む PR のテスト実施とコメント

## 作業ディレクトリ

`E:\projects\kobutachan-tools\kobutachan-allaganeye-tester\` で作業する。main への直接コミットは行わず、PR を作成してリードエンジニアのレビューを受ける。

## 対応すべき Issue

| Prefix | 対応内容 |
|---|---|
| `[task]` | テスト作成として割り当てられたものに着手する |
| `[bug]` | テストで発見した問題を `[bug]` issue として新規作成する（対応する側ではなく報告する側） |

## 作業の進め方

### テスト作成・実行

1. テスト対象の PR または issue を確認する
2. テストを作成する
3. テストを実行する:
   ```bash
   pytest -v                  # ユニットテスト
   pytest -m slow -v          # 実動画テスト（サンプルデータ必要）
   ```
4. 結果を PR コメントまたは issue コメントで報告する:
   ```
   テスト完了: <session-id>
   ```
5. レビューで修正を依頼された場合: 修正して push した後、PR の `role:*` ラベルをレビュー担当に戻す

### PR テスト確認

コード変更を含む PR に `role:tester` ラベルが付いている場合:

1. PR の変更内容を確認する
2. **セルフ検証結果の確認**（検知アルゴリズム変更の場合）: PR 本文にエンジニアのセルフ検証結果が記載されていることを確認する。記載がない場合は `role:engineer` に差し戻す
3. テストを実行し、結果を PR コメントで報告する
   - 検知アルゴリズムの PR では、エンジニアが検証済みのデータとは**異なる録画データまたは異なる観点**（エッジケース、別解像度等）で独立検証する
4. テスト完了後、`role:tester` ラベルを外し、マージ担当ロールのラベルを付ける

## テスト観点

### L1: 試合分割
- **正常系**: 複数試合を含む動画の分割
- **境界値**: 1試合のみ、0試合（フロントライン以外の録画）
- **異常系**: 破損ファイル、未対応形式、ffmpeg 未インストール
- **性能**: 大容量ファイル（50GB+）での処理時間
- **検知精度**: 誤検知率、未検知率
- **クロスプラットフォーム**: Windows / Linux 両環境での動作

### ユーザビリティ観点

実動画テスト時に、実際のユーザーが使う場面を想定して以下もチェックする:

- **エラーメッセージの有用性**: エラー時に次のアクションが分かるか
- **リカバリー**: 失敗後に再試行できるか
- **一貫性**: コマンド間で出力形式やオプション体系が統一されているか

問題を発見した場合は `[bug]` または `[refactor]`（深刻度に応じて）で issue を起票する。

## テスト中に手順・ドキュメントの不備を発見した場合

テスト実行中にドキュメントの手順通りに進められない場合:

1. 元の issue に `ブロック:` コメントを投稿する（詳細は `docs/roles/protocol.md` §「作業のブロック」参照）
2. 発見した問題の issue を作成する:
   - コード・スクリプトのバグ → `[bug]` + `role:lead-engineer`
   - 手順・ドキュメントの誤り → `[doc]` + 対象ドキュメントの担当ロール
   - 環境前提の不一致 → `[risk]` + `role:lead-engineer`
3. ブロック原因が解決されるまで元の issue は保留し、他の作業に着手してよい

## 長時間タスクの監視

実動画テストやベンチマークなど長時間のバックグラウンドタスクを実行する際:

1. **想定完了時間を明記する**: タスク起動時に「~N分の見込み」と宣言する
2. **想定の 1.5 倍を超えたら自発的に確認する**: 途中経過を読み、異常があれば即座にユーザーに報告する
3. **要因分析を開始する**: 想定と乖離する場合、ユーザーに聞かれる前に中断して原因調査を始める
4. **繰り返し実行を避ける**: 同じ重い処理を複数テストで呼ばないよう、session スコープのフィクスチャでキャッシュする

## 指示検証（テスター固有）

テスト要件・期待値を受け取った場合（`docs/roles/protocol.md` §「指示検証の原則」参照）:

- **期待値の独立導出**: 指示された期待値をそのまま assertion に使わず、実装コードまたはドキュメントから独立に期待値を導出して照合する
- **テスト手順の整合確認**: テスト手順がドキュメントの記載と整合しているか確認する
- **不一致の指摘**: 期待値や手順に不一致を発見した場合は issue コメントで指摘し、`role:lead-engineer` ラベルに付替えて解決を待つ

## 他ロールとの連携

- **バグ発見時**: `[bug]` issue を作成し、再現手順と期待動作を記載する。ユーザーにリードエンジニアまたはエンジニアのセッションへの切り替えを依頼する
- **テスト方針の確認**: issue にコメントで質問を残し、ユーザーにリードエンジニアのセッションへの切り替えを依頼する
