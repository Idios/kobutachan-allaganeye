# ロール間連携プロトコル

このドキュメントは全ロール共通のルールを定義する。各ロール定義ファイルより本プロトコルが優先される。

## 前提: セッション間の連携モデル

各ロールは独立した Claude Code セッションとして動作する。セッション間で直接通信する手段はない。

- **ユーザー（人間）がセッション間のハブ** となり、各セッションを切り替えて動かす
- ロール間の情報伝達は **GitHub Issues・PR・ファイルシステム** を介した非同期のやりとり
- 他ロールへの依頼や質問は issue として残し、自セッションの作業はそこで区切る
- ユーザーが対象ロールのセッションを起動し、issue を読ませて対応させる

## ロール一覧

| ロール | 責務 | 権限 |
|---|---|---|
| Director | 戦略的意思決定、プロセス管理 | PR マージ、リリース承認 |
| Lead Engineer | 設計、コードレビュー、技術的判断 | PR マージ、設計決定 |
| Engineer | 実装、リファクタリング、テスト作成 | PR 作成、Issue 対応 |
| Tester | テスト実行、品質検証、エッジケース発見 | テスト報告、Issue 作成 |

## セッション識別

- 各セッションはロール開始時に **セッション ID** を宣言する（例: `director-1`, `lead-1`, `engineer-1`, `tester-1`）
- 同一ロールの複数セッションはそれぞれ異なる ID を使う
- セッション ID は issue コメント、ブランチ名、コミットメッセージで使用する

## 情報の受け渡し場所

| 発信元 | 受信先 | 場所 |
|---|---|---|
| ディレクター | 全ロール | `docs/` 配下のドキュメント、GitHub Issues |
| リードエンジニア | エンジニア | GitHub Issues（タスク定義）、PR レビューコメント |
| リードエンジニア | テスター | GitHub Issues（テスト要件） |
| エンジニア | リードエンジニア | Issue コメント（指示の技術的不整合の指摘・差し戻し） |
| エンジニア | テスター | PR（テスト対象の明示） |
| テスター | リードエンジニア | Issue コメント（テスト要件と実装/ドキュメントの不一致指摘） |
| テスター | 全ロール | GitHub Issues（バグ報告）、PR コメント |

## Worktree 運用

各ロールは専用の Git Worktree で作業する。メインリポジトリ（`kobutachan-allaganeye/`）は人間が直接編集する場所として確保する。

### Worktree の配置

```
E:\projects\kobutachan-tools\
  kobutachan-allaganeye/              ← メインリポジトリ（人間が直接操作）
  kobutachan-allaganeye-director/     ← ディレクター用 worktree
  kobutachan-allaganeye-lead/         ← リードエンジニア用 worktree
  kobutachan-allaganeye-eng1/         ← エンジニア1用 worktree
  kobutachan-allaganeye-tester/       ← テスター用 worktree
```

### Worktree の作成

セッション開始時に worktree が未作成であれば、メインリポジトリで以下を実行する:

```bash
git worktree add ../kobutachan-allaganeye-<suffix> -b <session-id>/work
```

作業ブランチは issue 着手時に切り替える:

```bash
git checkout -b <session-id>/issue-<N>-<slug>
```

### 各セッションの作業ディレクトリ

Claude Code は **worktree のディレクトリで起動する**。メインリポジトリでは起動しない。

### ROLE ファイル

各 worktree のルートに `ROLE` ファイルを配置。内容はロール名のみ（例: `engineer`）。
SessionStart hook がこのファイルを読み、ロール適用を促す。

## ブランチとマージのルール

### ベースブランチ

- 各ロールの PR は **`develop-x.x.x`** にマージする（`main` ではない）
- `main` はリリース時の `develop-x.x.0 → main` マージのみ
- 現在の開発ブランチは `develop-0.1.0`
- 詳細は `docs/release-strategy.md` を参照

### 基本ルール

- **人間（ユーザー）**: main への直接コミット可
- **全ロールのセッション**: main への直接コミット不可。必ず PR 経由でマージする
- **PR 作成後は feature ブランチへの追加コミットを行わない**。PR を作成したら作業ブランチ（`<session-id>/work`）に戻る。追加の変更が必要になった場合は、まず `gh pr view <番号> --json state` で PR の状態を確認し、マージ済みなら新しいブランチを作成する

### PR レビューとマージ

#### レビュー担当の決定

PR に対応する元 issue がある場合、**issue の作成者ロール**がレビューする（作成者ロールが PR 作成者と異なる場合）。これにより、要件を最もよく理解しているロールがレビューを担当する。

元 issue がない場合（プロアクティブ改善等）、または issue 作成者と PR 作成者が同一ロールの場合は、以下のフォールバックテーブルに従う:

| PR 作成者 | フォールバックレビュー担当 |
|---|---|
| ディレクター | リードエンジニア |
| リードエンジニア | ディレクター |
| エンジニア | リードエンジニア |
| テスター | リードエンジニア |

issue 作成者ロールの判定方法: issue 本文末尾の `作成: <session-id>` からセッション ID のプレフィックスで判定する（`director-*` → ディレクター、`lead-*` → リードエンジニア、`engineer-*` → エンジニア、`tester-*` → テスター）。

#### マージ実行

マージはリードエンジニアまたはディレクターが行う。

- レビュー担当が lead/director の場合: レビュー担当がそのままマージする
- レビュー担当が engineer/tester の場合: LGTM 後、レビュー担当がラベルを lead/director に付替え、lead/director がマージする

レビューは PR コメントで行う。GitHub の approve 機能は使用しない（全ロールが同一アカウントのため self-approve 不可）。ユーザー（人間）が直接マージすることを妨げない。

マージ方法: `gh pr merge <番号> --squash`（1 PR = 1 コミットで履歴を簡潔に保つ）

### レビューでの修正依頼時

レビュー担当が PR に修正を依頼（差し戻し）した場合、`role:*` ラベルを PR 作成者のロールに付替える。修正完了後、PR 作成者がレビュー担当のロールに戻す。

```
PR 作成 → role:<レビュー担当>
  ↓ 修正依頼
  → role:<PR 作成者> に付替え（レビュー担当が実施）
  ↓ 修正完了・push
  → role:<レビュー担当> に戻す（PR 作成者が実施）
```

### レビューワラベルの管理

- `role:*` ラベルは「該当ロールに作業を依頼中」を示す
- 該当ロールが作業完了（レビュー承認、テスト完了等）後、ラベルを外す
- ラベルが残っている PR = まだ対応待ちの作業がある

### マージ前のテスト要件

コード変更を含む PR は、テスターの確認を経てからマージする。

| PR の内容 | マージ前の要件 |
|---|---|
| ソースコード (`allaganeye/`) | テスターがテスト実施し、PR にテスト結果コメント必須 |
| テストコード (`tests/`) | リードエンジニアのレビューのみ |
| ドキュメント (`docs/`, `CLAUDE.md`, `.claude/`) | リードエンジニアのレビューのみ |
| 混在（コード + ドキュメント） | コード変更に準じる（テスト必須） |

- テスト結果コメントは `テスト完了: <session-id>` + 実行結果の要約を含めること
- テスト結果コメントがない PR をマージしてはならない（ドキュメントのみの場合を除く）
- テスト完了コメント投稿後、テスターが `role:tester` ラベルを外し、マージ担当ロールのラベルを付ける。マージ担当は PR の既存の `role:*` ラベル（レビュー担当）と同じ。`role:tester` のみの PR（テスターがレビュー担当）の場合は以下のフォールバックに従う:

| PR 作成者ロール | テスト完了後に付けるラベル |
|---|---|
| エンジニア | `role:lead-engineer` |
| リードエンジニア | `role:director` |
| ディレクター | `role:lead-engineer` |

### PR 作成前の必須手順

PR を作成する前に、以下を必ず実施する。リベース不足による差し戻しを防ぐためのルール。

1. **ベースブランチの最新を取り込む**:
   ```bash
   git fetch origin develop-0.1.0
   git rebase origin/develop-0.1.0
   ```
2. **ローカルで CI 相当のチェックを実行する**:
   ```bash
   ruff check .
   ruff format --check .
   pytest
   ```
3. 上記がすべて通ることを確認してから PR を作成する

コンフリクトが発生した場合は解消してからチェックを再実行する。チェック未実施の PR はレビュー前に差し戻される。

### 実データ検証を伴う PR

実動画・実データの入出力に依存する処理（検知、OCR、音声認識、評価等）を変更する PR には、以下の追加手順が適用される。L1 では `allaganeye/video/` が対象。L3 以降でモジュールが追加された場合は本セクションの対象に含まれる。

#### エンジニアのセルフ検証

PR 提出前に、エンジニア自身が実動画でのセルフ検証を完了すること。テスターに初回発見を委ねない。

1. **実動画テストの実施**: 利用可能な録画データ（`ALLAGANEYE_SAMPLE_VIDEO_DIR`）で動作確認する
2. **退行チェック**: 変更前後の検出結果を比較し、退行がないことを確認する
3. **修正・再検証の反復**: 退行があれば修正→再検証を繰り返す。Lead への中間確認は不要
4. **エスカレーション条件**: 以下の場合のみ issue コメントで Lead に相談する:
   - 根本的な設計判断が必要な問題に当たった場合
   - 修正の方向性が複数あり自力で判断できない場合
   - 特定の録画でどうしても退行を解消できない場合
5. **PR 本文への記載**: セルフ検証結果を PR 本文に記載する:
   - 使用した録画データ（ファイル名またはディレクトリ）
   - 検出数の Before / After
   - 既知の制約がある場合はその旨

#### Lead レビュー時の確認

セルフ検証結果が PR 本文に記載されていない場合、コードレビュー前に差し戻すこと。記載がある場合は、内容の妥当性を技術的裁量で判断する。運用実績が蓄積されてから定量基準を策定する。

#### テスターの独立検証

テスターは、エンジニアのセルフ検証とは**異なる録画データまたは異なる観点**で独立検証を行う。エンジニアが既に検証済みのデータで同じ確認を繰り返す必要はない。セルフ検証結果が PR に記載されていない場合は `role:engineer` に差し戻す。

### PR 作成時のラベルとアサイン

PR 作成時に以下を必ず付与する:

- **アサイン**: `--assignee Idios`
- **ロールラベル**: レビュー担当ロールの `role:*` ラベル（§「レビュー担当の決定」に従い、元 issue の作成者ロールまたはフォールバックテーブルから決定）
- **テスターラベル**: コード変更（`allaganeye/`）を含む PR で、レビュー担当がテスター以外の場合は `role:tester` も付与する（テスト実施のため）
- **`Closes`/`Fixes`/`Resolves` 禁止**: PR 本文・コミットメッセージでこれらのキーワードを使わない。issue のクローズは PR マージ後に手動で行う（§「PR マージ後（クローズ）」参照）

## ブランチ命名規則

```
<session-id>/issue-<N>-<slug>
```

例: `engineer-1/issue-15-add-validation`, `tester-1/issue-20-smoke-test`

## Issue のライフサイクル

### 排他制御

- 1つの issue には同時に1つのセッションだけが着手できる
- 着手時: issue にコメントで `着手: <session-id>` と宣言する
- 他セッションが `着手:` コメント済みの issue には着手しない

### 作業完了時

PR を作成したら、関連 issue に対して以下を行う:

1. **完了コメント**: `完了: <session-id> → PR #番号`（対応内容の要約を添える）
2. **`role:*` ラベルの付替え**: 次に行動すべきロール（= PR のレビュー担当）に変更する
3. **チェックボックスの更新**: issue 本文にチェックボックスがあれば、完了した項目をチェックする（`gh issue edit --body` で更新）

| 作業者ロール | 付替え先 |
|---|---|
| ディレクター | `role:lead-engineer` |
| リードエンジニア | `role:director` |
| エンジニア | `role:lead-engineer` |
| テスター | `role:lead-engineer` |

### PR マージ後（クローズ）

マージ実行者（= レビュー担当）が、関連 issue を **クローズ** する。

- issue 本文に未チェックのチェックボックスが残っている場合はクローズせず、作成者ロールにラベルを付替える（`作成: <session-id>` から判定）
- 詳細は [`docs/issue-policy.md`](../issue-policy.md) §7 参照

## 作業のブロック

着手済みの issue が外部要因（手順の不備、環境前提の不一致、他 issue への依存など）で進行不能になった場合の対応手順。

### ブロック発生時

1. **元の issue にブロックコメント**: `ブロック: <session-id> ← #番号 (<理由の要約>)`
2. **ブロック原因の issue を作成する**（下記の判断基準に従う）
3. 元の issue の着手状態は維持する（他セッションは着手しない）
4. ブロック原因が解決されるまで元の issue は保留し、**他の作業に着手してよい**

### ブロック原因の issue 作成基準

| 発見した問題 | prefix | 起票先 |
|---|---|---|
| スクリプト・コードのバグ | `[bug]` | `role:lead-engineer` |
| ドキュメント・手順の誤り | `[doc]` | 対象ドキュメントの担当ロール |
| 環境前提の不一致・想定外の状況 | `[risk]` | `role:lead-engineer` |
| 判断できない場合 | `[question]` | `role:lead-engineer` |

### ブロック解除後

ブロック原因の issue が解決（PR マージ等）されたら:

1. 元の issue にコメント: `再開: <session-id> ← #番号 解決済み`
2. 作業を再開する（新たな `着手:` コメントは不要）

## 作業発見の標準手順

セッション開始時または作業が一区切りしたとき、次の作業を探すには `/check-work` コマンドを使う。

- ロールに応じた Issue・PR の候補を自動で調査・分類する
- ユーザーが選択するまで着手しない（`着手:` コメントは自動では投稿しない）
- 対象外（着手済み・方針待ち）は明示的に除外して表示する

## コミットルール

- 関連する issue がある修正にはコミットメッセージに `#番号` を含める
- `Closes` / `Fixes` / `Resolves` キーワードは使わない（issue のクローズは手動で行う）
- コミットメッセージの末尾に `[<session-id>]` を含める

## ユーザーへの差分提示

PR 発行前にユーザーの判断を仰ぎたい場合、以下のいずれかの方法で差分を提示する。

1. **チャット内で `git diff` を実行して出力を見せる**（推奨）
2. **VSCode マルチルートワークスペースでの確認を促す**

差分を提示する際は、変更の意図と懸案点を簡潔に説明してからユーザーに判断を求める。

## Plan モードの使用

複雑なタスク（複数ファイルの変更、設計判断を伴う作業、影響範囲の広い修正）に着手する際は、まず Plan モード（`/plan`）で計画を立て、ユーザーの確認を得てから実装に入る。

- 計画には変更対象ファイル、変更の方針、考慮すべきリスクを含める
- ユーザーが計画を承認した後に実装を開始する
- 単純な修正（typo 修正、1ファイルの小さな変更など）には不要

## サブエージェントの活用

リードエンジニア・エンジニア・テスターは、調査や検索をサブエージェントに委譲し、メインコンテキストを本来の作業に集中させること。

- コードベースの探索・検索には Explore サブエージェントを使う
- 複数の独立した調査は並列でサブエージェントに委譲する
- サブエージェントの結果はメインコンテキストに要約して取り込む
- まず軽量モデル（haiku / sonnet）で試み、結果が不十分な場合はより高性能なモデルで再実行してよい

※ ディレクターは通常のドキュメント・issue 作業では不要だが、整合性チェック等の複数ファイル横断調査では使用してよい

## 指示検証の原則

他ロールからの指示・方針を受けた場合、**自ロールの専門性で技術的妥当性を検証してから着手する**。「指示されたから正しい」ではなく「検証して納得したから着手する」が基本姿勢。

### 全ロール共通

- 指示に含まれる数値・前提条件・期待結果を、自ロールの知見で検算・検証する
- 不整合を発見した場合は issue コメントで **具体的な箇所と根拠** を記載し、指示元ロールに差し戻す
- 差し戻し時は `role:*` ラベルを指示元ロールに付替え、解決を待つか他の作業に着手する
- 差し戻しは品質向上のフィードバックであり、推奨される行動である

### ロール別の検証観点

| ロール | 指示元 | 検証すべき観点 |
|---|---|---|
| Director | Lead（技術提案・リスク報告） | 根拠データが提示されているか。既存の方針文書（ロードマップ・release-strategy 等）と矛盾しないか。コスト/効果の見積もりが妥当か |
| Lead Engineer | Director（優先順位・スコープ）、Tester（バグ報告） | 現在のアーキテクチャで実現可能か。バグ報告がバグ/仕様/環境依存のどれか切り分け |
| Engineer | Lead（実装方針・数値指定） | 指示された数値をエッジケースで検算。新パラメータが既存 CLI オプション・設定値と矛盾しないか |
| Tester | Lead / Issue（テスト要件・期待値） | 期待値を実装コードまたはドキュメントから独立に導出して照合。テスト手順がドキュメントと整合するか |

## 問題の報告義務

作業中に発見した問題・懸念・制約は、重大度に関わらず必ず記録に残すこと。**問題を過小評価して報告しない、または独自に先送りを判断してはならない**。

### 報告の原則

- 発見した問題は **issue の作成** または **関連 issue・PR へのコメント** として記録する
- 「軽微だから」「後で対処するから」「スコープ外だから」という理由で報告を省略しない
- 先送りが妥当な場合でも、まず記録してから先送りの判断を適切なロールに委ねる

### 報告先の判断

| 発見した問題 | 報告方法 |
|---|---|
| 作業中の issue・PR に直接関係する問題 | 該当 issue・PR にコメント |
| 作業中の issue・PR のスコープ外の問題 | 新規 issue を作成（§「作業のブロック」のプレフィックス基準に従う） |
| 先送りが妥当と思われる問題 | 新規 issue を作成し、本文に先送り理由を記載。判断はディレクターまたはリードエンジニアが行う |

### 禁止事項

- 問題を認識しながら報告せずに作業を続行すること
- 「Phase N で対応」「L2 以降で対応」等の先送りを、issue を作成せずにコミットメッセージやコード内コメントだけで記録すること
- レビューやテストで発見した問題を「想定内」と自己判断して報告を省略すること

## 作業の境界

- 各ロールは自分の権限範囲外の作業を行わない
- **作業はドキュメント（`docs/`）とソースコードに記載された手順・仕様に基づいて進める。ドキュメントに記載のない手順を独自に実施しない**。手順の不足・矛盾を発見した場合は `[doc]` issue を起票し、ドキュメントが修正されてから作業を再開する（§「作業のブロック」参照）
- **外部動画データの取り扱い**: Idios 以外のユーザーが提供した動画ファイルは、`allaganeye-guard verify` が PASS するまで allaganeye で処理しない（詳細は [`docs/guard-integration.md`](../guard-integration.md) §8 参照）
- 判断に迷う場合はユーザーに確認する
- 他ロールの成果物を変更する必要がある場合は issue を作成して依頼する
