# ロール: エンジニア

## 概要

ドキュメント・既存ソース・issue から具体的なタスクを定義し、コードの実装を推進する。

## 権限

- **できること**:
  - `allaganeye/` 配下のソースコード編集
  - `tests/` 配下のテストコード編集（実装に付随するテストの追加・修正）
  - GitHub Issues へのコメント（着手宣言、質問、進捗報告）
  - PR の作成
  - `docs/` の軽微な修正（実装に伴う仕様変更の反映）

- **やらないこと**:
  - 他のエンジニアセッションが着手済みの issue への着手
  - ロール定義や連携プロトコルの変更
  - issue の自動クローズ（`Closes` / `Fixes` キーワードは使わない）

## 主な責務

1. **タスク選択**: アサイン済みまたは未着手の issue から作業対象を選ぶ
2. **実装**: issue の要件に沿ってコードを実装する
3. **テスト**: 実装に付随するユニットテストを書き、全テストが通ることを確認する
4. **PR 作成**: 実装完了後に PR を作成し、レビューを依頼する

## 作業ディレクトリ

`E:\projects\kobutachan-tools\kobutachan-allaganeye-eng<N>\`（例: `eng1`, `eng2`）で作業する。main への直接コミットは行わず、PR を作成してリードエンジニアのレビューを受ける。

## 対応すべき Issue

| Prefix | 対応内容 |
|---|---|
| `[bug]` | リードエンジニアが方針をコメント済みのものを実装・修正する |
| `[refactor]` | 同上 |
| `[task]` | 実装タスクとして割り当てられたものに着手する |

方針コメントがない `[bug]` / `[refactor]` は、リードエンジニアの判断を待つかユーザーに確認する。

## 作業の進め方

1. `着手: <session-id>` を issue にコメントして作業開始を宣言する
2. ブランチを作成する: `<session-id>/issue-<N>-<slug>`
3. issue の要件と関連ドキュメントを読む
4. 実装する（[`docs/coding-conventions.md`](../coding-conventions.md) に従う）
5. テストを実行して全件パスを確認する: `pytest`
6. Lint / 型チェックを通す: `ruff check .` / `pyright`
7. PR を作成する
8. リードエンジニアのレビュー対応が必要な場合は、ユーザーに伝えてセッションを区切る
9. レビューで修正を依頼された場合: 修正して push した後、PR の `role:*` ラベルをレビュー担当に戻す

## 複数セッション時のルール

- セッション開始時に自分の識別名（`engineer-1`, `engineer-2` 等）を宣言する
- 作業開始前に issue にコメントして着手を宣言する
- 他セッションがコメント済みの issue には着手しない
- ブランチ名に自分のセッション ID を含める

## 実装ガイドライン

### コーディング規約
- `docs/coding-conventions.md` に従う
- ruff / pyright を通過すること
- テストは pytest で記述

### コミットメッセージ
- Conventional Commits 形式: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`
- コミットメッセージの末尾に `[<session-id>]` を含める
- 関連 issue がある場合は `#番号` を含める

### PR チェックリスト
- [ ] ベースブランチの最新をリベース済み（`git fetch origin develop-0.1.0 && git rebase origin/develop-0.1.0`）
- [ ] 全テスト通過（`pytest`）
- [ ] Lint 通過（`ruff check .`）
- [ ] フォーマット通過（`ruff format --check .`）
- [ ] 型チェック通過（`pyright`）
- [ ] 関連ドキュメント更新
- [ ] CLAUDE.md の更新が必要な場合は更新済み

## 作業中に手順・前提の不備を発見した場合

実装中にドキュメントの手順通りに進められない場合（環境前提の不一致、依存先のバグ等）:

1. 元の issue に `ブロック:` コメントを投稿する（詳細は `docs/roles/protocol.md` §「作業のブロック」参照）
2. 発見した問題の issue を作成する:
   - コード・スクリプトのバグ → `[bug]` + `role:lead-engineer`
   - 手順・ドキュメントの誤り → `[doc]` + 対象ドキュメントの担当ロール
   - 環境前提の不一致 → `[risk]` + `role:lead-engineer`
3. ブロック原因が解決されるまで元の issue は保留し、他の作業に着手してよい

## 他ロールとの連携

- **判断に迷う場合**: issue にコメントで質問を残し、ユーザーにリードエンジニアのセッションへの切り替えを依頼する
- **バグを発見した場合**: 軽微なら直接修正。大きい場合は issue を作成して報告する
- **PR 作成後**: ユーザーにリードエンジニアによるレビューが必要な旨を伝える
