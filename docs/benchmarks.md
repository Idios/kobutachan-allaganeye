## GPU vs CPU ベンチマーク

`--dry-run` での検知時間（分割は含まない）。

| モード | 検出数 | 実行時間 | sample_interval | 備考 |
|---|---|---|---|---|
| CPU (`--no-gpu`) | 7/7 | 7m12s | 2.0s (auto) | max_workers=24 |
| GPU (`--gpu`) | 7/7 | 7m50s | 2.0s (auto) | チャンク並列 GPU デコード |

### 分析

- **AV1 入力では CPU モードが GPU より高速**。AV1 の GPU デコード支援は H.264/HEVC ほど成熟していない
- CPU 並列プローブ（max_workers=24）は per-probe のデコードコストが小さいため、AV1 でも十分高速
- GPU モードが有利になる想定ケース:
  - H.264/HEVC 入力（GPU デコード支援が効率的）
  - 低コア数 CPU 環境（並列プローブの並列度が低い）
  - 長時間動画で sample_interval=1.0 を使用する場合（プローブ数が多い）

## 性能改善の推移

37GB/60fps AV1 MKV (121.7min) での計測。

| 時点 | 実行時間 | 手法 | PR |
|---|---|---|---|
| 初期（OpenCV） | 計測不能（不安定） | OpenCV VideoCapture | — |
| 並列 `-ss` プローブ | ~24min | max_workers=8, interval=1.0 | #57 |
| max_workers + auto-interval | ~7min | max_workers=24, interval=2.0 | #69 |
| 2パス精密計測追加 | ~7min | +~400 refine probes（オーバーヘッド軽微） | #79 |
| GPU モード | ~7m50s | チャンク並列 GPU デコード | #91 |

### ボトルネックの変遷

1. **初期**: OpenCV の MKV シーク不安定で計測不能
2. **並列 `-ss` (#57)**: プロセス起動 ×7300 + キーフレーム距離デコードがボトルネック
3. **max_workers + auto-interval (#69)**: workers 8→24 で ~3x、interval 1.0→2.0 でプローブ数半減。合計 ~3.4x 改善
4. **現在**: per-probe のデコードコスト（キーフレーム距離に比例）が支配的。これ以上の改善にはアーキテクチャ変更が必要

## 環境依存の性能特性

### コーデック別

デコードコスト（大→小）: **AV1 > HEVC > H.264**

- AV1: キーフレーム間隔が大きく、per-probe のデコードコストが高い。GPU 支援の効果も限定的
- HEVC: AV1 より軽量。GPU 支援あり（NVDEC 対応）
- H.264: 最も軽量。GPU 支援が最も成熟しており、GPU モードの恩恵が最大

### ストレージ

- **SSD 推奨**。並列プローブで同時に複数のシーク I/O が発生するため、HDD ではボトルネックになる可能性がある
- GPU モード（チャンク並列）はシーケンシャル読み取りに近いため、HDD でも CPU モードより有利な可能性がある（未検証）

### CPU コア数

- `max_workers` のデフォルトは `min(cpu_count, 24)`
- 32コア環境: workers=24 で十分な並列度（残りのコアは OS + ffmpeg プロセスに使用）
- 8コア環境: workers=8 が上限。処理時間は 32コア比で ~3x 長くなる想定
- `--workers` で明示指定可能
