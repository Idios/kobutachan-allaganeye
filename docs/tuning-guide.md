# パラメータ調整ガイド

このガイドでは、試合の分割がうまくいかない場合の対処法を説明します。

## 正常に動作するケース

デフォルト設定は以下の条件を満たす録画に合わせて調整されています。多くの場合、パラメータを変更する必要はありません。

- **FF14 フロントライン（FL）の録画**であること
- **複数試合を含む長時間録画**であること（試合間に暗転が入る）
- **OBS 等の画面キャプチャ録画**であること（MP4 / MKV 形式）
- 試合間のロード画面（暗転）が **2 秒以上**続くこと

### うまく動作しない可能性があるケース

| ケース | 理由 |
| --- | --- |
| FL 以外のコンテンツ | 暗転パターンが異なるため検知できない |
| 1 試合のみの録画 | 試合間の暗転がないため境界が見つからない |
| 暗転が極端に短い録画 | サンプリング間隔で拾えない場合がある |
| フェード効果を使用 | OBS のシーン切替でフェードを設定していると暗転が短くなる |

うまくいかない場合は、以下の推奨ワークフローに従ってパラメータを調整してください。

## 推奨ワークフロー

### 1. まず `--dry-run` で検知結果を確認する

いきなり分割するのではなく、まず `--dry-run` で検知結果だけを確認しましょう。動画ファイルの分割は行われず、検知された試合の一覧だけが表示されます。

```bash
allaganeye split your_recording.mkv --dry-run
```

出力例:

```text
  Match 1:   00:00 -   15:17  (15m17s)  [unknown]
  Match 2:   18:49 -   34:51  (16m01s)
  Match 3:   40:37 -   57:53  (17m15s)
```

`[unknown]` マーカーが付いた試合は録画の開始/終了が試合途中だった可能性がある不完全セグメントです（#382）。マーカーなしは FL 試合として完全検知されたもの。

自分の録画を見返して、この結果が実際の試合の切れ目と合っているか確認してください。

### 2. 問題があればパラメータを調整する

下の「症状別の対処法」を参考に、パラメータを変更して再度 `--dry-run` で確認します。

**ヒント**: 閾値の調整で迷う場合は `debug-brightness` コマンドで特定区間のフレーム輝度を確認できます。

```bash
# 試合間の暗転がありそうな区間の輝度を確認
allaganeye debug-brightness your_recording.mkv --start 900 --end 1000 --interval 0.5
```

CSV 形式（`timestamp,brightness`）で出力されるので、暗転部分の輝度を確認し `--blackout-threshold` の値を決める参考にしてください。

### 3. 結果が正しければ本実行する

```bash
allaganeye split your_recording.mkv
```

## 症状別の対処法

### 試合の途中で分断されてしまう

**症状**: 1試合が2つ以上のファイルに分かれてしまう。

**原因**: ダウン→リスポーン時の短い暗転（1-2秒）を試合の切れ目と誤判定している。

**対処**: `--min-blackout-duration` を上げる。

```bash
# デフォルト: 3.0秒 → 5.0秒に変更
allaganeye split your_recording.mkv --min-blackout-duration 5.0 --dry-run
```

**値の決め方**: リスポーン時の暗転は通常 1-2 秒、試合間のロード画面暗転は 5 秒以上です。両者の間の値を指定します。デフォルトの 3.0 秒で多くの場合は十分ですが、分断が起きる場合は 4.0 → 5.0 と少しずつ上げてください。10.0 以上にすると本来の試合間暗転も無視される可能性があるため、上げすぎに注意してください。

**内部動作の補足**: 2パス精密計測（0.25s 間隔）により、暗転の持続時間を高精度に計測しています。精密計測後のフィルタリングでは `min(指定値, 1.5)` が適用されるため、`--min-blackout-duration` を 1.5 より大きく設定しても、1.5秒以上の暗転はすべて境界候補として残ります。これは 2.0s 程度の短い試合間暗転（パターン C）を検出するための設計です。1.5s 以下を指定した場合はその値がそのまま使用されます。さらに、スコアバーフィルタリング（#111）により、暗転の前後に FL のスコアバーがあるかを検査して誤検知を除去するため、デフォルト設定のままでもリスポーン暗転の誤検知は大幅に抑制されています。

---

### 別々の試合がくっついてしまう

**症状**: 2試合以上が1つのファイルにまとまってしまう。出力される試合数が実際より少ない。

**原因**: 試合間の暗転が検知されていない。ロード画面が完全な黒画面ではなく、少し明るい場合に起きやすい。

**対処**: `--blackout-threshold` を上げる。

```bash
# デフォルト: 15.0 → 25.0 に変更
allaganeye split your_recording.mkv --blackout-threshold 25.0 --dry-run
```

**値の決め方**: この値は画面の明るさを 0（真っ黒）〜 255（真っ白）で表した閾値です。この値以下の明るさのフレームが「暗転」と判定されます。

- 15.0（デフォルト）: ほぼ真っ黒なフレームだけを検知
- 20.0-30.0: 少し明るいロード画面も検知
- 40.0 以上: 通常のゲーム画面も暗転と誤判定する可能性あり

まずは 20.0 → 25.0 と 5 刻みで試し、試合が正しく分かれるところを探してください。

---

### 短い試合が出力されない

**症状**: 途中退出や途中参加で短かった試合のファイルが出力されない。

**原因**: デフォルトでは 300 秒（5分）未満のセグメントは「試合ではない」として除外されている。

**対処**: `--min-match-duration` を下げる。

```bash
# デフォルト: 300秒 → 60秒に変更
allaganeye split your_recording.mkv --min-match-duration 60 --dry-run
```

**値の決め方**: フロントラインの通常の試合は 15-20 分です。途中参加でも 5 分以上プレイしていればデフォルトで問題ありません。それより短い試合を含めたい場合は、含めたい最短の時間（秒数）を指定してください。ただし、あまり短くすると待機画面やロビーの映像も1つのファイルとして出力される場合があります。

---

### 試合が1つも検知されない

**症状**: Exit code 4 で「試合境界が見つからない」エラーになる。

**考えられる原因と対処**:

1. **動画がフロントラインの録画ではない**: このツールはフロントラインの試合間暗転（ロード画面）を検知して分割します。フロントライン以外の録画では暗転パターンが異なるため、検知できません。

2. **1試合だけの録画**: 試合間に暗転がないため、分割する境界が見つかりません。分割の必要がない録画です。

3. **暗転の閾値が低すぎる**: `--blackout-threshold` を上げてみてください（上記「別々の試合がくっついてしまう」を参照）。

4. **録画ソフトの設定**: OBS 等でシーン切替時にフェードを入れている場合、暗転が短くなることがあります。`--min-blackout-duration` を下げてみてください。

5. **チャット欄マスクを合成した録画**: 配信のチャット欄を隠すマスク画像を全画面に合成している録画では、暗転部分もマスクに覆われて検知できないことがあります。暗転が 1 件も検出できなかった録画では、mask のない領域を自動検出して再検知する fallback が `--masked` 未指定でも自動で発動します。暗転が一部だけ見つかって結果が合わない場合は、`--masked` を指定してこの経路を強制してください（#821 / #822）。発動したかどうかは `metadata.json` の `detection_params.masked_fallback_used` で確認できます。

6. **VTuber 配信の録画（ゲーム画面が inset）**: ゲーム画面が画面の一部に縮小配置され、装飾オーバーレイが重なる録画では、試合間の暗転が画面全体の暗転として現れません。`--vtuber` を指定すると、暗転ではなく「試合中である」証拠（スコアバーの有無 × 画面の動き）の timeline から試合区間を抽出します（#895）。`--masked` との同時指定は排他エラー（exit 5）になります。

### 処理が遅い

**症状**: 大容量ファイル（50GB 以上）で処理に時間がかかる。

**対処 1: `--sample-interval` を上げる**

```bash
# デフォルト: 1.0秒 → 2.0秒に変更
allaganeye split your_recording.mkv --sample-interval 2.0
```

**値の決め方**: この値は動画の何秒ごとにフレームをチェックするかを指定します。

- 1.0（デフォルト）: 1秒ごとにチェック。最も正確だが最も遅い
- 2.0: 2秒ごと。処理時間が約半分になる。ほとんどの場合十分な精度
- 5.0: 5秒ごと。高速だが、短い暗転（5秒未満）を見逃す可能性あり

フロントラインの試合間暗転は通常 5 秒以上あるため、2.0 秒でも精度はほぼ変わりません。10.0 以上にすると暗転を見逃す可能性が高くなるため推奨しません。

**自動調整**: `--sample-interval` を指定しない場合、動画の長さに応じて自動で調整されます（1h超→2.0s、2h超→3.0s）。明示的に指定した場合は自動調整は無効になります。

**対処 2: `--workers` でワーカー数を指定する**

```bash
# CPU コア数が多い環境で並列数を増やす
allaganeye split your_recording.mkv --workers 16
```

デフォルトでは CPU コア数に応じたワーカー数が自動設定されます（上限は実装側の cap に従います。正は `allaganeye/video/detector.py` の `_resolve_workers` docstring）。通常は変更不要ですが、他のプロセスとリソースを共有する場合は下げることも検討してください。

**対処 3: `--gpu` で GPU アクセラレーションを使う**

```bash
allaganeye split your_recording.mkv --gpu
```

GPU 対応環境（NVIDIA CUDA, Intel QSV 等）では、暗転検知の処理を GPU で高速化できます。動画をチャンクに分割し、各チャンクで長寿命の ffmpeg プロセスを GPU デコードで並列実行します。GPU が利用できない場合は自動で CPU モードにフォールバックします。

#### CPU と GPU の使い分け

どちらが速いかは**コーデックと環境によって異なります**。一般的な傾向:

| コーデック | 推奨モード | 理由 |
| --- | --- | --- |
| H.264 | GPU (`--gpu`) | GPU デコード支援が最も成熟しており、恩恵が大きい |
| HEVC (H.265) | GPU (`--gpu`) | GPU 支援あり。AV1 より効率的 |
| AV1 | GPU (`--gpu`) (NVDEC RTX 30+ / QSV Arc・Gen12+ / VCN 4.0+) | #414 で GPU auto-select 対象に追加。対応 GPU で decode 成功、未対応環境では自動で CPU フォールバック |
| VP9 | GPU (`--gpu`) — Intel QSV は HW decode (#582), NVIDIA / AMD は soft (#538) | #414 で GPU auto-select 対象。NVIDIA は #538 で `vp9_cuvid` + swscaler gray 変換の非互換のため `-hwaccel auto` 経路で soft decode (speed 2.64x)。AMD d3d11va 用 dict には vp9 未登録で同様に soft fallback。Intel は #582 で `vp9_qsv` 登録、Tiger Lake で 8.29x speed (HW decode) 動作確認 |

低コア数 CPU（4-8 コア）では、GPU モードが有利になりやすい傾向があります。

#### GPU vendor の選択 (`--gpu-vendor`, #546 / #553 / #550 / #582)

実装済み vendor は NVIDIA (#546) / AMD (#553) / Intel (#550) の 3 つ。複数 GPU 環境では、デフォルトで NVIDIA dGPU が選択されます (`_VENDOR_PREFERENCE` = nvidia > amd > intel)。明示的に vendor を指定したい場合は `--gpu-vendor` オプションを使ってください。

```bash
# NVIDIA GPU を明示使用 (dual GPU 環境で dGPU を強制)
allaganeye split your_recording.mkv --gpu --gpu-vendor nvidia

# AMD iGPU / dGPU を明示使用 (NVIDIA 不在 or AMD-only 環境)
allaganeye split your_recording.mkv --gpu --gpu-vendor amd

# Intel iGPU を明示使用 (NVIDIA / AMD 不在 or Intel 単独環境)
allaganeye split your_recording.mkv --gpu --gpu-vendor intel

# 自動選択 (既定値、--gpu-vendor 省略時と同じ)
allaganeye split your_recording.mkv --gpu --gpu-vendor auto
```

| Vendor | 対応状況 | 備考 |
| --- | --- | --- |
| `nvidia` | 実装済み (#546) | NVDEC cuvid 経由、h264 / hevc / av1 対応 |
| `amd` | 実装済み (#553) | d3d11va + native decoder + `hwdownload,format=nv12` 経由、h264 / hevc / av1 対応。RDNA2+ iGPU (Granite Ridge) で SW 比 3x 高速 |
| `intel` | 実装済み (#550 / #582) | QSV 経由 (`-hwaccel qsv -hwaccel_output_format qsv` + `hwdownload,format=nv12`)、h264 / hevc / vp9 / av1 対応。AV1 は Alder Lake (12th gen) / Arc 以降のハードウェアで decode 可能。Tiger Lake (11th gen Iris Xe) は av1_qsv 非対応のため AV1 入力時は自動で CPU fallback (h264 / hevc / vp9 は QSV decode 動作確認済み) |
| `auto` | 自動選択 | probe 結果から `_VENDOR_PREFERENCE` 順に実装済み vendor を選択 (NVIDIA > AMD > Intel) |

**Intel QSV の追加引数 (実装メモ)**: Intel QSV は default で GPU surface (`pix_fmt=qsv`) を出力し、後段の swscaler が gray 変換時に `Function not implemented (-40)` で失敗します。`_decode_chunk` は AMD d3d11va と同じ `_HWACCELS_NEED_HWDOWNLOAD` 機構を再利用し、vendor=intel のとき自動で `-hwaccel_output_format qsv` を付与しつつ filter chain 先頭に `hwdownload,format=nv12,` を挿入します。実機ベンチ (i7-1185G7 / Iris Xe): h264_qsv 13.7x / hevc_qsv (720p) 3.76x (#550) / vp9_qsv (720p) 8.29x (#582)。

#### ベンチマークで判断する

自分の環境で最適なモードを判断するには、`--dry-run` で両方のモードを試して比較してください。`--dry-run` では動画の分割を行わないため、検知処理の速度だけを比較できます。

```bash
# CPU モードで計測
allaganeye split your_recording.mkv --dry-run --no-gpu

# GPU モードで計測
allaganeye split your_recording.mkv --dry-run --gpu
```

実行時間と検出数を比較し、速いほうを本実行で使用してください。検出数が同じであれば、速いほうを選べば問題ありません。

> 参考: 実測データは [`docs/benchmarks.md`](benchmarks.md) を参照してください。

## パラメータ一覧

| パラメータ | デフォルト | 範囲 | 説明 |
| --- | --- | --- | --- |
| `--blackout-threshold` | 15.0 | 0.0 - 255.0 | 暗転と判定する明るさの上限。大きくすると検知が緩くなる |
| `--min-match-duration` | 300.0 | 0 以上 | この秒数未満のセグメントを除外する |
| `--min-blackout-duration` | 3.0 | 0 以上 | この秒数未満の暗転を無視する（リスポーン暗転の除外用） |
| `--sample-interval` | 1.0 | 0 より大きい値 | フレームチェックの間隔（秒）。大きくすると高速だが精度が下がる |
| `--workers` | auto | 1 以上 | 並列ワーカー数。auto は CPU コア数から実装の cap で解決される (正: `_resolve_workers` docstring) |
| `--gpu` / `--no-gpu` | auto | - | GPU アクセラレーション検知。**どちらも指定しない場合はコーデックから自動選択** (H.264/HEVC/AV1/VP9 → GPU、それ以外 → CPU、#414)。利用不可時は CPU フォールバック |
| `--masked` | false | - | チャット欄マスク画像が全画面に合成された録画向け。mask のない領域を自動検出して再検知する。暗転が 1 件も検出できなかった場合は未指定でも自動発動し、本フラグは暗転が一部見つかる場合でもこの経路を強制する (#821 / #822) |
| `--vtuber` | false | - | VTuber 配信録画（ゲーム画面が inset）向けの timeline 検出。暗転ではなくスコアバーの有無 × 画面の動きから試合区間を抽出する。`--masked` との同時指定は排他エラー (exit 5) (#895) |
| `--keep-trailing` | false | - | 試合終了後の trailing 区間を通常の試合として分割出力する。デフォルトは metadata に `post_match: true` で保持しつつ分割 MP4 からは除外する (#805) |

## よくある質問

### デフォルト設定のまま使っても大丈夫？

はい。デフォルト値はフロントラインの一般的な録画に合わせて調整されています。多くの場合、パラメータを変更する必要はありません。うまくいかない場合だけ、このガイドを参考に調整してください。

### 分割後の動画の画質は変わる？

変わりません。映像・音声を再エンコード（変換）せず、そのままコピーして分割するため、元の画質がそのまま維持されます。

### 分割に失敗した場合、やり直せる？

はい。再度同じコマンドを実行すれば、出力ファイルは自動的に上書きされます。途中で失敗した場合も、成功済みのファイルはそのまま残ります。
