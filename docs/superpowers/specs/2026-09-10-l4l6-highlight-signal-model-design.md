# L4-L6 ハイライト検出：活躍の定量定義・信号モデル 設計

- **日付**: 2026-09-10
- **状態**: Design（issue #1048 対応。Track 2 Phase 0）
- **対象**: allaganeye 0.4.0（L4/L5/L6 統合）の「自プレイヤーの活躍検出→切り抜き」機能の信号モデル
- **前提 doc**: [`2026-09-04-v040-roadmap.md`](./2026-09-04-v040-roadmap.md) §1.2
- **関連 issue**: #1048（本 spec）/ #1047（自プレイヤー識別方式比較）/ #1046（採用技術選定）/ #1049（rule-based ストリークスコアリング）/ #1050（ハイライト範囲 UI）

## 1. 背景・目的

録画動画から「自プレイヤーが活躍した瞬間」を検出し、ハイライトとして切り抜く。ロードマップ §1.2 の「初期主信号 = キル・アシストのストリーク」を、**画面上に表示される自プレイヤー専用 UI の変化**として直接かつ単純に検出する形へ具体化する。

## 2. 確定したドメイン仕様（信号の根拠）

出所: FF14 公式攻略情報 + 実録画（キルストリーク場面の 4K 切り抜き、2026-09-11 マルチモーダル解析）。

### 2.1 戦意値ゲージ（自プレイヤー専用 UI）

- 画面に**自プレイヤー自身の戦意値ゲージのみ**表示。他プレイヤーのゲージは表示されない。
- 見た目: 赤い紋章 + 白い「戦意値（この録画では 100）」数字 + 金色の横ゲージ。
- 戦意値は最大 100（戦意高揚 V）。**最大値到達中は KO してもゲージ値が変化しない**（飽和）。

### 2.2 KO/ASSIST インジケータ（検出対象）

- 戦意値ゲージの**直下**に、「`<数字> K.O.!!`」形式のテキストが表示される。
- KO 発生のたびに**同じ HUD 領域で数字が書き換わる**（1 回の KO = カウント +1、「6 → 7 → … → 12」と連続更新）。スタック（並び表示）しない。
- 見た目: 数字は淡い黄白色/クリーム色（目安 `#FFF5C8`）、`K.O.!!` はほぼ白（`#FFFCFF`）、暗い縁取り + 背後に黒〜濃灰の半透明横帯。
- 単発 KO の表示時間目安: 約 1.5s。連続 KO 時は次の更新まで約 0.15〜0.35s（ただし**単発 KO の標準表示時間は現時点で未確定**、Phase 1 で実測）。

### 2.3 表示位置（最重要制約）

- 位置は**プレイヤーの UI 設定で可変**。固定座標を仮定できない。
- 参考（特定録画での実測、4K=3840×2160）: KO テキストは x≈1280〜1515・y≈1267〜1310（画面比率 左33〜40%・上59〜61%）。戦意値ゲージは概ね x≈1160〜1605・y≈1140〜1265、KO テキストの直上。
- この位置は**当該プレイヤーの設定依存**であり、別プレイヤーでは変わる。検出には動的位置解決が必須。

## 3. 設計の要点

- **初期主信号 = KO/ASSIST インジケータ（「数字 + K.O.!!」テキスト）の出現・更新の検出**、の 1 つに絞る。
- 戦意値ゲージの**値の読取りは不要**（偽陽性・飽和・位置可変の問題を回避）。
- LB ゲージ、キルログ OCR（kill feed）、効果音は**初期実装から除外**（将来の拡張信号として位置づけ）。

> **なぜ値ではなく「K.O.!! テキスト」か**: 戦意値は自分が直接 KO しなくても増える（ドローン討伐等）ため、値上昇は偽陽性を含む。また飽和時は値が動かない。一方「`n K.O.!!`」テキストは**自分自身の KO・アシストの発生に対応**して表示され、飽和と独立に機能する。よって最も直接的で堅牢な主信号である。

## 4. 自プレイヤー識別との関係（#1047 への含意）

- KO インジケータ・戦意値ゲージは**自プレイヤー専用 UI**であるため、検出対象をこの UI に限定すれば「自プレイヤー識別」を実質バイパスできる。
- ただし**位置可変**のため、「自プレイヤー UI の位置をどう特定するか」という「**UI 領域解決**」問題が残る（§6）。
- この UI 領域解決は、#1047 の「自プレイヤー識別」とは**別軸**の問題として扱う（#1047 はプレイヤー名指定を基本とする想定の別 issue）。

## 5. 拡張可能な信号モデル

将来の信号追加（例: 単騎で敵アライアンスを足止めしてチーム勝利に寄与）を想定し、プラガブルな信号 + スコアリングに設計する。

### 5.1 信号（Signal）の共通インタフェース

各信号は単一の「活躍の兆候」を検出し、タイムスタンプ付きスコアを返す。将来の追加は Signal 実装を足すだけにする。

```
Signal.detect(frames) -> list[HighlightEvent]
HighlightEvent:
  signal_id      # 信号識別子 (例: "ko_assist_indicator")
  timestamp      # 動画内絶対時間 (秒)
  score          # 0..1 の信頼度/強度
  evidence       # 検出根拠 (例: 検出した数字、変化量、テンプレ一致度)
```

### 5.2 初期信号（Phase 1 対象）

| signal_id | 名称 | 検出方法 | 実装層 |
| --- | --- | --- | --- |
| `ko_assist_indicator` | KO/ASSIST インジケータ | 戦意値ゲージ直下の「数字 + K.O.!!」テキスト出現・更新を検出 | L4 |

> **補助・将来信号（Phase 1 以降）**: キルログ OCR（`kill_feed`、#125）、LB リセット（`lb_reset`）、効果音。初期主信号を補完・検証する位置づけ。

### 5.3 スコアリング（L5、#1049）

- MVP は rule-based（ロードマップ Q2.6）。
- `ko_assist_indicator` の検出時刻を時間窓で束ね、**連続性（ストリーク）**を「ハイライト価値」としてスコア化。
- 詳細は #1049 に委ね、本 spec は信号の定義と拡張性の契約に留める。

## 6. KO インジケータの位置動的解決（位置可変への対応）

UI 位置が可変なため、検出前に KO インジケータ領域を動的に解決する。Phase 0 では方式を定め、実装は Phase 1。

### 6.1 候補方式

| 方式 | 概要 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A. 初回キャリブレーション | ユーザーが初回に KO 表示領域を指定（minimap crop #481/#893 と同様の UI） | 確実・単純 | 初回手間 / レイアウト変更で再設定 |
| B. 特徴テンプレマッチ走査 | 「数字 + K.O.!!」の見た目（淡黄白テキスト + 暗帯）を全画面走査 | 自動 | テクスチャ管理 / 誤検出 |

> **方針**: 初期は **A（初回キャリブレーション）** を基本とし、既存の minimap crop GUI（#893）の「領域指定 UI」を再利用する。B は Phase 1 後に精度検証して採用可否を判断（#1046 技術選定と連動）。

### 6.2 領域の永続化

解決した KO インジケータ領域は metadata.json の `capture_regions`（既存 RegionTimeline serialize 形、#810 / #824）と同様の枠組みで永続化することを想定。詳細は L4 実装で確定。

## 7. 受け入れ条件（GT 判定基準）

「ハイライト」判定が検証可能になるよう、GT 突合の基準を定める。

- **GT の定義**: 手動アノテーションで「自プレイヤーの KO/ASSIST 発生時刻（KO インジケータの更新時刻）」を付与した動画。
- **判定基準（初期）**:
  - `ko_assist_indicator`: GT の KO/ASSIST 発生時刻に対し、検出時刻が ±0.5s 以内でマッチする率（recall）と誤検出（precision）を評価。
- **回帰テスト**: ロードマップ Q4.1「新機能 highlight には GT/baseline 回帰テストを追加」に従い、サンプル動画群での評価分布を CI で再現可能にする。

## 9. リスク・留意点

- **単発 KO の標準表示時間が未確定**（連続 KO のみの録画からは測定不可）。Phase 1 で単発 KO 場面の録画を追加取得して実測する。
- **位置可変**が最大リスク。初回キャリブレーション + 多フレーム consensus で緩和するが、レイアウト変更への追随は別途検討。
- **KO インジケータの見た目（色・大きさ）は HUD テーマ・解像度で変わりうる**。公式で確認できたのは 1 録画のみ。Phase 1 実装前に複数録画で外観のばらつきを確認する。
- 「K.O.!!」と同時に ASSIST がどのように表示されるか（別表記か、同じカウントか）は未確認。Phase 1 で確認し、信号定義を補正する。
