## 2. 実測方法

**前後端（表示区間）と bbox / 色で手法を分けている。混同すると再現性が壊れるため明記する。**

1. **前後端（表示区間）**: 申告時刻の前後を **0.1 秒刻み**で切り出し、テキスト帯（1080p: x 580–800 / y 615–670）を 3 倍拡大して**目視**で判定した。
   本 note の表示区間はすべて**この目視値**であり、量子化誤差は ±0.1 秒。
2. **補助のテンプレートマッチ**: 493.5 秒フレームの **`K.O.!!` 部分のみ**（数字を含まない `f[626:660, 680:756]`）をテンプレートに `TM_CCOEFF_NORMED` を取った。
   **ただし前後端の確定には使っていない** —— 白い戦闘エフェクトで誤検出し、閾値 0.70 では 493.43–493.77 秒しか拾えず目視区間（493.2–494.7 秒）と一致しなかったため。
3. **bbox と色**: 各表示区間の**中央フレーム**（KO: 494.0 秒 / ASSIST: 207.0 秒）から、帯域 x 560–820 / y 632–662 を切り出し、
   HSV しきい値（V ≥ 205 / S ≤ 125）でテキスト画素を抽出した。縦に連結成分を取り、**面積 15 px 以上の成分のみ**残し、
   残った全成分の和集合 bbox と、**同じ残存画素だけの** BGR 平均を報告値とした（bbox と色で母集団を揃えている）。

> **計測の限界**: 背景が白い戦闘エフェクトのとき、明るさだけの判定は誤検出する（実測でも偽陽性が多数出た）。
> 前後端は目視、bbox / 色は中央フレームのマスクという分担にしてあり、単一のヒューリスティックに依存していない。

## 3. 実測結果

### 3.1 KO インジケータ

| 項目 | 実測値 |
| --- | --- |
| テキスト | `N K.O.!!`（N は連続カウント。実測は `1 K.O.!!`） |
| 位置（マスク bbox） | x **665–731** / y **634–651**（グリッド計測による目視の外接矩形は x ≈660–755。マスクしきい値 V ≥ 205 で先頭の数字と右端の `!!` が落ちる） |
| 画面比（マスク bbox 基準） | 左 **34.6–38.1%** / 上 **58.7–60.3%** |
| 表示区間 | **493.2–494.7 秒（約 1.5 秒）**（0.1 秒刻みの目視判定） |
| 出現/消滅 | 左からスライド + フェードイン（493.2 では左端が欠ける）、494.6 からフェードアウト |
| 色 | 白系 `#F8F6EF`（面積フィルタ後の画素平均 BGR 239/246/248 = R248 G246 B239、HSV 平均 S≈9 / V≈248）+ 濃い縁取り |
| 同時変化 | 戦意値 48 → 56（+8） |

**spec との一致**: 2026-09-10 spec §2.2 は「単発 KO の標準表示時間は未確定（約 1.5s 目安）」としていた。
本実測で **約 1.5 秒**を確認した。位置も spec の 4K 実測値（左 33–40% / 上 59–61%）と整合する。

#### 3.1.1 桁数が増えたときの位置（左右アンカーの実測）

**KO 数は KO ごとに増える。テキストは数字を含むため、桁数が変わると文字列の幅が変わる。**
アンカーが固定だと検出 ROI とテンプレートがずれるため、1 桁と 2 桁を実測して比較した。

| 例 | 動画 / 時刻 | x 範囲（目視） | 幅 | 中心 |
| --- | --- | --- | --- | --- |
| `1 K.O.!!` | `20260116_1.mp4` 493.5 秒 | **≈ 660–755** | ≈ 95 px | **≈ 707** |
| `12K.O.!!` | `20260116_5.mp4` 788.5 秒 | **≈ 640–775** | ≈ 135 px | **≈ 707** |

**結論: テキストは水平方向に「中心固定」で伸びる可能性が高い**（中心 x ≈ 707 が両方で一致）。
1 桁→ 2 桁では左右に約 20 px ずつ広がった。ただし:

- **これは 2 サンプルの差であって、「1 桁増えるごとに 20 px」という不変量ではない**（3 桁以上はサポート対象外、HUD スケールも可変）
- **`K.O.!!` 部分は右へずれる**。位置を固定したテンプレートでは 2 桁目以降で外れるため、実装は位置探索が必須
- 比較は同じアニメーション位相（表示が安定した区間の中央）で行った。フェードイン/アウトの端では文字が欠けて幅が小さく出るため、
  端のフレーム同士を比べると中心がずれて見える（§3.1 のマスク bbox が目視外接矩形より狭いのも同じ理由）
- 数字と `K.O.!!` の間の空白は**保証されない**（2 桁例は `12K.O.!!`）。テキスト一致は `K.O.!!` を単位にする

### 3.2 ASSIST インジケータ

| 項目 | 実測値 |
| --- | --- |
| テキスト | `ASSISTED!`（**数値プレフィックスなし**。KO の `N K.O.!!` とは書式が異なる） |
| 位置（マスク bbox） | x **602–756** / y **636–649**（目視の外接矩形もほぼ同じ） |
| 画面比（マスク bbox 基準） | 左 **31.4–39.4%** / 上 **58.9–60.1%** |
| 表示区間 | **206.4–207.9 秒（約 1.5 秒）**（0.1 秒刻みの目視判定） |
| 出現/消滅 | 左からスライドイン（206.4 では左端が欠ける）、207.8 でフェードアウト |
| 色 | 暖色寄りの白 `#F5F1E2`（面積フィルタ後の画素平均 BGR 226/241/245 = R245 G241 B226、HSV 平均 S≈20 / V≈245）+ 金色の縁取り。KO より彩度が高い（S 9 → 20） |
| 同時変化 | 戦意値 44（KO の +8 に相当する変化は観測していない） |

**重要**: ASSIST は KO と同じ**テキスト帯**（y 630 前後）に出るが、**書式が全く違う**（数字なし・別単語）。
したがって「KO テキストの数字更新」と「ASSISTED! の出現」を**別々のテンプレートで検出**する必要がある
（2026-09-10 spec §2.2 / §3 の「別の信号として扱う」方針と一致）。

### 3.3 併設 UI（戦意値ゲージ）の実測

KO / ASSIST テキストの直上に自プレイヤー専用の戦意値ゲージがある（spec §2.1）。

| 要素 | 位置（1080p） |
| --- | --- |
| アイコン | x 585–645 / y 582–615 |
| 数値 | x 725–770 / y 597–615 |
| ゲージバー | x 647–775 / y 620–630 |

- 数値は実測で 20 / 32 / 40 / 44 / 48 / 56 / 64 / 84 / 92 / 96 / 100 を観測（spec §2.1 の最大 100 と一致）
- 戦意値の段階でアイコンの色・形が変化（低: 緑リング → 高: 黄色い六角 → 100: 赤リング）
- テキストは常にゲージバーの直下に表示される（本録画では位置が固定）

### 3.4 同一帯域に出る「別のテキスト」（BOOSTED!）—— 誤検知の主要因

他プレイヤーの録画（`2772549129-…mp4`、1080p）で、**同じ帯域に 3 種類のテキストが出る**ことを確認した。

| 表示 | 発生条件 | 扱い |
| --- | --- | --- |
| `N K.O.!!` | 自プレイヤーの KO | **検出対象**（`ko_indicator`） |
| `ASSISTED!` | 自プレイヤーのアシスト | **検出対象**（`assist_indicator`） |
| `BOOSTED!` | **ドローン撃破などによる戦意値上昇**（KO でもアシストでもない） | **無視（未知クラス）** |

実測（`2772549129-…mp4` / 1080p）:

| 時刻 | テキスト | 位置 |
| --- | --- | --- |
| 5:57 (357 秒) | `BOOSTED!` | x ≈610–760 / y ≈320–345 |
| 11:10 (670 秒) | `ASSISTED!` | x ≈610–765 / y ≈322–348 |
| 12:42 (762.4 秒) | `4 K.O.!!` | x ≈655–770 / y ≈330–355 |

**3 種は位置・サイズ・色（白 + 縁取り）がほぼ同じで、文字列だけが違う。**
したがって「帯域に白テキストが出たら KO」という判定は**必ず誤検知する**。
**文字列レベルの識別が必須**。ただし分類は **`K.O.!!` / `ASSISTED!` の 2 つの正例 + それ以外（未知）は無視** とする
（`BOOSTED!` を個別クラスとして固定しない。未知の表示が将来増えても既定で無視されるほうが安全）。

### 3.5 別プレイヤーでの相対配置の確認（§4-4 の仮定の検証、n=1）

同 VOD では HUD スケールが参照と異なり、**表示位置も全く違う**（参照: 画面下部 y ≈634 / 本 VOD: 画面上部 y ≈330）。
一方で**相対配置は保たれている**:

| 関係 | 参照（Idios） | 他プレイヤー VOD |
| --- | --- | --- |
| ゲージバー幅 | ≈130 px | ≈180 px（**≈1.4 倍**） |
| テキスト高さ | ≈17 px | ≈25 px（**≈1.5 倍**） |
| テキストの位置 | バー直下・バー中心付近 | 同じ（バー直下・中心付近） |

**結論**: 「ゲージとテキストが同じ UI 要素として一緒に拡縮する」という §4-4 の仮定は、
**この 1 例では支持される**（スケール比がゲージ ≈1.4 / テキスト ≈1.5 で一致し、相対位置も同じ）。
ただし**視覚読み取りの誤差は ±10 px 程度**あり、n=1 なので断定はしない（§5 の未実測を参照）。

## 4. 実装への含意

1. **位置とスケールは動画ごとに異なる —— 絶対ピクセル値を実装定数にしない（最重要）**:
   インジケータの表示位置・サイズは **プレイヤーの HUD レイアウト設定**で変わり、**画面解像度**でも変わる。
   本 note §3 の座標は「参照レイアウト（1080p / このプレイヤーのこの設定）」の記録であり、**実装の定数ではない**。

   **実測でもサンプル間で座標が一致しなかった**: §3.1.1 の 1 桁と 2 桁は同じプレイヤーの同日録画だが、
   x 座標は完全一致していない。この差には**桁数の差と録画間の位置差が混在**しており、本 note では分離できていない。
   いずれにせよ「録画ごとにキャリブレーションする」前提が必要（位置を定数化しない）。

2. **アンカーは「常時表示の戦意値ゲージ」にする**: KO テキストは KO 時にしか出ないため、キャリブレーションには使えない。
   戦意値ゲージは試合中常に表示され、形状（像アイコン + バー）が特異なのでアンカーに適する。
3. **キャリブレーション手順（動画ごとに 1 回）**:
   1. 数フレーム（例: 試合開始付近の 5–10 フレーム）で**多スケール探索**（template を 0.5–2.5 倍、step 0.1 程度）して
      ゲージを検出し、**スケール係数 s** と基準点を求める
   2. テキスト帯は**相対幾何**で算出する（絶対座標を使わない）
   3. 検出時は ROI を s で**正規化サイズにリサイズ**してから単一スケールで照合する（テンプレートは 1 種類でよい）
   4. キャリブレーション失敗、または検出結果の連続性が崩れたら**再キャリブレーション**する。
      それでも失敗する場合は**ユーザー指定領域へフォールバック**し、**黙って検出ゼロにしない**（失敗を明示する）
   5. 解決した領域とスケールは metadata に永続化する（既存 `capture_regions` / RegionTimeline の枠組み、`#810` / `#824`）
4. **相対幾何の実測比（参照、1080p / このレイアウト）**:

   | 関係 | 実測（1080p） | バー高さ h で正規化 |
   | --- | --- | --- |
   | バー | x ≈650–780 / y ≈620–630 | h ≈ 10 px |
   | テキスト上端 | ≈634（バー下端 +4） | +0.4 h |
   | テキスト高さ | ≈17 | ≈1.7 h |
   | テキスト中心 | ≈707（バー中心 ≈715） | −0.8 h |

   **この比率は「同じ UI 要素なので HUD スケールで一緒に拡縮する」という仮定に依存している**。
   仮定が崩れるケース（ゲージとテキストが別スケールになる設定）は**未検証**であり、
   実装時は「比率で当てた位置で検出できなかったらアンカーを再探索する」二段構えにする。
5. **検出帯域は相対値で定義する（バー幅基準）**: 絶対 x ではなく、**ゲージバーの幅 w と下端**から導出する。
   実測のテキスト外接矩形を包含する**余白込みの帯域**は次のとおり（w = 128 px @1080p の実測値から逆算）:

   | 方向 | 定義 | 根拠（実測） |
   | --- | --- | --- |
   | 横 | `bar_left − 0.5w` 〜 `bar_right + 0.15w` | 最も左は `ASSISTED!` の 602 px（bar_left 647 の 0.35w 左）、最も右は KO の 775 px（bar_right） |
   | 縦 | `bar_bottom − 0.05w` 〜 `bar_bottom + 0.3w` | テキストの完全な外接矩形は y 626–660（高さ 34 px ≈ 0.27w）。§4-6 のテンプレート（34×100 px）が収まる高さを確保する。マスク bbox（y 634–651）を基準にすると狭すぎる |

   **バー高さ h（≈10 px）を基準にしない**: h は小さく量子化誤差が大きいため、`k·h` で幅を決めると狭すぎる
   （例: k=3, h=10 では 60 px 幅になり、95–154 px のテキストを包含できない）。**バー幅 w を基準にし、実測の外接矩形を包含する余白を取る**
6. **テンプレートは位置探索付きで使う（2 正例 + 未知は無視）**: 帯域で検出したテキストを、
   **`K.O.!!` → `ko_indicator` / `ASSISTED!` → `assist_indicator` / どちらにも一致しない → 無視** の 3 分岐で扱う。
   **`BOOSTED!` は「どちらにも一致しない」の実例**（§3.4。ドローン撃破等で戦意値が上がるだけで KO でもアシストでもない）。
   未知の表示を個別クラスとして列挙しないことで、将来追加される表示にも自動で追従する（誤検知の既定が「無視」になる）。
   「白テキストが出たら KO」という判定は誤検知するので禁止。KO は数字部分が可変で、
   しかも **1 桁と 2 桁の実測で `K.O.!!` の位置が約 20 px ずれた**（§3.1.1。増分が一定とは限らない）ので、
   固定座標の crop ではなく **帯域全体に対する `matchTemplate` の最大値と位置**を取る。
   KO の基準テンプレートは参照レイアウトで **34×76 pxの接尾辞のみ**（`f[626:660, 680:756]`。数字を含めない）。
   **スケールの扱いは 1 通りに固定する**: §4-3.3 の「ROI を参照サイズに正規化する」を採り、**テンプレートは参照サイズのまま**使う
   （テンプレートを s 倍する方式と併用しない — 両方やるとサイズが食い違って照合が壊れる）。
   数字と `K.O.!!` の間の空白は保証されない（`12K.O.!!`）ので、テンプレートは `K.O.!!` 部分のみで作る
7. **カウント値は OCR しない**: 数字を読む必要はなく、「`K.O.!!` の**出現**を 1 KO」「表示中の数字領域の変化を連続 KO」として数える。
   数字の OCR はフォント・解像度依存が大きく、本信号の目的（時刻の抽出）に対して過剰
8. **マッチスコアの実測分布（閾値の根拠にはならない）**: 目視区間（493.2–494.7 秒）を 0.1 秒刻みで評価した
   `TM_CCOEFF_NORMED` のマックスコアは **0.42–1.00** に広く分布し、0.70 以上は **493.5–493.7 秒の 3 点のみ**だった
   （接尾辞のみのテンプレートで再測した値）。
   つまり「0.70 を閾値にすれば検出できる」とは言えない（背景を含む ROI では背景がスコアを支配する）。
   実装時は (a) 色・輝度マスクと組み合わせる、(b) エッジや輪郭（縁取り）を使う、などの改善が必要。
   **0.7 は実測で妥当性を確認した値ではない**（初期候補としての出発点にすぎない）
9. **標本間隔**: 連続 KO では次の更新が 0.15–0.35 秒で来る（2026-09-10 spec §2.2 の観測）。
   **この短い更新を取りこぼさないため**、検出のフレーム間隔は 0.1 秒以下が望ましい。
   単発表示（約 1.5 秒）自体は 0.5 秒間隔でも捉えられる —— 律速するのは連続更新の間隔である
10. **前後端の定義**: 本 note の表示区間は**目視値を 0.1 秒で量子化したもの**。実装で使う場合の候補は
   「スコアが閾値を最初に超えた時刻」だが、**本 note の値はその定義ではない**（実測でもテンプレートマッチ単独は
   493.43–493.77 秒しか拾わず、目視区間と一致しなかった）。実装側で閾値ベースの定義を採る場合は、
   GT 突合で前後端のずれを評価すること

## 5. 未実測 / 残課題

- **別 HUD 配置での観測**: 参照（Idios の録画）に加え、他プレイヤーの配信 VOD 1 本で **位置が全く異なること** と
  **相対配置・スケール比が保たれること**（§3.5、n=1）を確認済。ただし **2 例のみ**で、
  spec §9 の「位置の揺れ」を一般化するには GT を増やす必要がある（#1106 の GT 要件: 1 本以上を別配置で）
- **`BOOSTED!` 以外の未知表示**: 「2 正例 + 未知は無視」の設計により、未列挙の表示は既定で無視される（誤検知しない）。
  ただし**未知表示が正例に類似して高スコアを出す場合**（例: `K.O.` を部分文字列に含む表示）は誤検知しうるので、
  誤検知クラスの棚卸は運用で続ける
- **倍率の定量**: §3.5 のスケール比（ゲージ ≈1.4 / テキスト ≈1.5）は目視読み取りで ±10 px の誤差を含む。
  厳密な倍率はキャリブレーション実装時にテンプレートマッチのスコアで決めるべき
- **別 UI スケール設定での検証**: §4-4 の相対幾何は「ゲージとテキストが一緒に拡縮する」仮定に依存している。
  §3.5 の 1 例（他プレイヤー、スケール比 ≈1.4）では支持されたが、**HUD 設定を意図的に変えた録画での検証は未実施**
- **配信 VOD を GT に使う場合の制約（実測）**: オーバーレイ付きの配信 VOD はゲーム画面が右にオフセット・縮小されている。
  このため**全画面のスケール探索（0.3–1.2 倍）では同定できなかった**（`TM_CCOEFF_NORMED` の最大 0.69）。
  §3.4 / §3.5 の計測は、**時刻が既知の前提で目視により位置を特定**して実施した。
  GT を自動収集する場合は、オーバーレイなしの一人称録画を優先すること
- **3 桁以上の KO カウント**: **サポート対象外（2026-11-12 Idios 判断。3 桁を撮るのが困難なため）**。
  1–2 桁は実測済みで、2 桁でも中心固定で伸びることを確認済み。帯域も 1–2 桁を包含する幅で定義している
- **4K での実測**: **ネイティブ 4K（3840×2160）の実ファイルは手元に無い**（2026-11-12 時点で 1080p 72 本 / 3440×1440 28 本）。
  Idios の環境は **4K 表示を FHD で録画**しているため、本 note の 1080p 実測は「4K UI を 0.5 倍に縮小したもの」に相当する。
  この理解は spec §2.2 の 4K 座標と整合する（÷2 すると x 640–757.5 / y 633.5–655 で、実測 660–755 / 634–651 とほぼ一致）。
  **ネイティブ 4K 録画での直接実測は未実施**だが、解像度差はキャリブレーションのスケール s で吸収する設計（§4-3）なので px 値の網羅は不要
- **ASSIST のカウント**: `ASSISTED!` に数値は付かない。連続アシスト時の表示更新（再表示か延長か）は未観測
- **KO の連続時**: 連続 KO（次の更新が 0.15–0.35 秒）の実測は未実施（本 note は 1 桁 1 件 + 2 桁 1 件のみ）
- **HUD テーマ依存**: 色・大きさのテーマ依存は未評価（spec §9）

## 6. 再現手順

前後端は目視、bbox / 色は中央フレームのマスクで取る。以下のスクリプトが本 note の数値を再現する
（`VIDEO` と時刻だけ差し替えれば他の録画にも使える）。

```bash
# 前後端の目視確認（0.1 秒刻みで切り出し、画像を並べて判定）
ffmpeg -ss <t> -i <video> -frames:v 1 -vf "crop=210:55:590:615,scale=630:165:flags=neighbor" out.png
```

```python
import cv2, numpy as np

VIDEO = r"<video path>"


def frame_at(t: float) -> np.ndarray:
    cap = cv2.VideoCapture(VIDEO)
    cap.set(cv2.CAP_PROP_POS_MSEC, t * 1000)
    cap.grab()
    ok, f = cap.retrieve()
    cap.release()
    assert ok
    return f


# bbox / 色: 表示区間の中央フレームで計測（KO: 494.0 / ASSIST: 207.0）
Y0, X0, H, W = 632, 560, 30, 260  # 1080p のテキスト帯（ゲージバーを含めない）
band = frame_at(494.0)[Y0 : Y0 + H, X0 : X0 + W]
hsv = cv2.cvtColor(band, cv2.COLOR_BGR2HSV)
mask = cv2.inRange(hsv, (0, 0, 205), (45, 125, 255))  # V>=205, S<=125
n, labels, stats, _ = cv2.connectedComponentsWithStats(mask, 8)
keep = np.zeros_like(mask)
for i in range(1, n):
    if stats[i, 4] >= 15:  # 面積 15 px 未満を捨てる
        keep[labels == i] = 255
ys, xs = np.where(keep > 0)  # bbox と色で同じ母集団を使う
print("bbox", X0 + xs.min(), X0 + xs.max(), Y0 + ys.min(), Y0 + ys.max())
print("mean BGR", band[ys, xs].astype(float).mean(axis=0).round(0))

# スコア分布（前後端の確定には使わない参考値）
cap = cv2.VideoCapture(VIDEO)
cap.set(cv2.CAP_PROP_POS_MSEC, 493.5 * 1000)
cap.grab()
ok, f = cap.retrieve()
cap.release()
tpl = cv2.cvtColor(
    f[626:660, 680:756], cv2.COLOR_BGR2GRAY
)  # 接尾辞 K.O.!! のみ（数字を含めない）
for i in range(16):
    t = 493.2 + i * 0.1
    sub = cv2.cvtColor(frame_at(t)[626:660, 620:800], cv2.COLOR_BGR2GRAY)
    print(
        round(t, 1),
        round(float(cv2.matchTemplate(sub, tpl, cv2.TM_CCOEFF_NORMED).max()), 2),
    )
```

> **bbox はテキスト全体より狭く出る場合がある**: しきい値 V ≥ 205 は先頭の数字（`1`）や右端の `!!` の細い画素を落とすことがある。
> そのため §3 の位置は、グリッド計測で確認した**テキスト全体の外接矩形**（KO 1 桁: x ≈660–755）と、マスク由来の bbox を併記する形にしている。
