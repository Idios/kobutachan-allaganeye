- **目的**: #1049（L6 価値評価）のスコア関数と、その GT 検証方法を確定する
- **前提**: 信号モデルは
  [`2026-09-10-l4l6-highlight-signal-model-design.md`](2026-09-10-l4l6-highlight-signal-model-design.md)
  が正（**履歴として本文を書き換えない**。本 note は 5.3 節の既定 ±5 秒を

## 1. 決定事項

Idios 判断:

| # | 論点 | 決定 |
| --- | --- | --- |
| Q1(B) | スコアの構成要素 | **重み付き長さ（KO > ASSIST）+ 密度**。試合文脈（スコア差・残り時間）は 0.4.0 では使わない |
| Q2(C) | ストリークの窓 | **既定は ±10 秒**（2026-11-26）で、`window_seconds` で**調整可能**。spec の ±5 秒からの変更理由は 1.1 節 |
| Q3(B) | 検証方法 | **全ストリークを 3 段階（強 / 中 / 弱）で人手採点**し、モデルスコアとの **Spearman 相関**で評価する（採点は Idios の作業。基準は 5.1 節） |
| Q4(B) | 出力 | `metadata.highlights[]`（root、`{index, match_index, start, end, score, event_positions, signal_ids}`）。**write-back は L7 (#135) で行う**。本 phase は型と計算まで |

### Q1 で試合文脈を落とした理由

スコア差・残り時間といった試合文脈は `metadata.json` に系列として存在しない
（`matches[]` にあるのは境界時刻だけ）。文脈を入れるには試合中のスコアバーを
0.1 秒刻みで読む新しい信号抽出が必要で、+-数点の精度向上に対して検出系の
追加コストが見合わない。**0.4.0 はイベント列だけで完結させる**。将来
`signal_id` を増やせば同じ `ScoringEvent` 正規化で吸収できる（3 節）。

### 1.1 spec の既定（±5 秒）を ±10 秒に変えた理由

GT イベント 87 件（6 節）を ±5 秒で束ねると **63 ストリークのうち 45 件（71%）が
単独イベント**になり、スコアは **11 種類しか出ず、うち 38 件が 0.372 に完全同点**
（単独 ASSIST）になった。順位付けの道具としては識別力がなさすぎる。

±10 秒では 51 ストリーク / 単独 27 件 / 25 種類のスコアになり、同じイベント列から
より多くの順序情報が取れる。**「単独でも価値のある場面は拾いたいが、連続した
活躍をより高く見たい」** というスコア式の意図にも合う。

- **差分**: 信号モデル spec 5.3 節の「既定は前後 ±5 秒」を、本 note で ±10 秒に
  上書きする。spec 本文は履歴なので書き換えない
- **調整可能性**: `DEFAULT_WINDOW_SECONDS` と `window_seconds` 引数で変えられる。
  CLI / GUI からの指定は、L6 の実行面を作る L7 (#135) で公開する（本 phase は
  ライブラリ関数まで）

## 2. 信号 → ストリークへの正規化

metadata の `events[]` はレイヤー間の契約なので、スコア関数は生の dict を読まない。
`ScoringEvent.from_signal()` が `signal_id` を内部の `kind` に写す:

| `signal_id` | `kind` | provenance（スコアに影響しない） |
| --- | --- | --- |
| `ko_indicator` | `ko` | `position`（metadata 内の 1 始まり索引） |
| `assist_indicator` | `assist` | `signal_id` / `match_index` |
| 未知の値 | （捨てる） | — |

- **未知 `signal_id` は None を返して無視する**。イベント形式 spec §1 の
  「consumer は未知 `signal_id` を既定で無視する」をそのまま実装したもので、
  信号を足しても既存の読み手が壊れない。
- 非有限の `timestamp` / `end` は捨てる（`NaN` を 1 件混ぜるとソートが壊れ、
  以降のストリークが全滅するため、入口で落とす）。
- `end < start` は `end = start` に**丸める**（捨てない）。`end` はスコアに
  寄与せず（§4）、`Highlight.end` の表示にだけ効くため、欠測より丸めが安全。

## 3. 束ね方（ストリークの定義）

```text
sort events by (start, end, kind)
for each event: if same match_index and event.start - last_event.start <= window:
                    append to current group
                else: start a new group
```

**判定に使うのは直前イベントの「発生時刻」で、表示終了時刻ではない。** spec ±5 秒の
記述は「あるイベントの前後 5 秒以内に別の KO / ASSIST があれば同一ストリーク」だが、
表示長（`.evidence.samples` 由来の `end`）に依存させると同じ試合でも HUD や
走査 fps で境界が動いてしまう。発生時刻の差だけで閉じれば、`end` の推定精度から独立する。

**`match_index` が変わったら必ず切る。** 連続する試合の最終イベントと次の試合の
最初のイベントは、試合間の暗転が短いと窓（10 秒）に収まってしまう（実例: 前試合の
最後の KO と次試合の最初の KO が 6 秒差）。またいで束ねると `Streak.match_index` が
片方の試合を名乗り、L7 のクリップ範囲が**別試合をまたぐ**。`match_index` が `None`
（どの試合区間にも入らないイベント）はそれ自体を 1 つの区画として扱う。

この規則は**連鎖**する（推移的閉包）:

| 発生時刻 | 結果 |
| --- | --- |
| 3 / 6 / 9 秒（3 秒刻み） | 1 本（3 件）。合計 span は 6 秒だが隣接差がすべて 5 秒以内 |
| 3 / 9 秒（6 秒差） | 2 本（各 1 件） |

「ストリーク全体の幅が窓以内」ではなく連鎖を採るのは、`KO → 4 秒後 ASSIST →
8 秒後 KO` のような**実際の連続した活躍**を 1 本にまとめるため。幅で切ると
この例が 2 本に割れる。

`window_seconds` は有限かつ非負を要求する（`0` は「同時刻のみ束ねる」、
負値と非有限は `ValueError`）。非有限 `start` のイベントは束ねの前に落とす。

## 4. スコア式

```text
weighted     = ko_weight * ko_count + assist_weight * assist_count
length_term  = weighted / (weighted + saturation)          # 0..1 へ単調飽和
span         = 最後の event.start - 最初の event.start
density      = size / max(span + window, 1e-6)
density_term = min(1, density / full_density)
score        = length_share * length_term + (1 - length_share) * density_term
             = round(clamp(score, 0, 1), 3)
```

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `ko_weight` | 1.0 | 基準。KO は 1 試合あたり GT 実測 4-11 回 |
| `assist_weight` | 0.35 | ASSIST は KO の 3-4 倍出るため同数なら KO を高く評価する。**GT 後に調整する前提の初期値** |
| `saturation` | 1.5 | 重み付き件数が増えても 1.0 に張り付かないための飽和点 |
| `full_density` | 0.25 | 「1 秒あたり 0.25 件」で密度項が満点 |
| `length_share` | 0.7 | 長さ項 7 : 密度項 3 |

### 計算例（既定 ±10 秒）

| ストリーク | length_term | density_term | score |
| --- | --- | --- | --- |
| 単独 KO | 1/2.5 = 0.400 | 1/10/0.25 = 0.400 | **0.400** |
| 単独 ASSIST | 0.35/1.85 = 0.189 | 0.400 | **0.252** |
| KO + ASSIST（2 秒差） | 1.35/2.85 = 0.474 | 2/12/0.25 = 0.667 | **0.532** |
| KO x2（1 秒差） | 2/3.5 = 0.571 | 2/11/0.25 = 0.727 | **0.618** |
| KO x2（0.5 秒差） | 0.571 | 2/10.5/0.25 = 0.762 | **0.629** |

**単独イベントの密度項は `1 / window` に反比例する**（`span = 0` のため）。
つまり `window` はスコアの**絶対水準**を動かす（+-5 秒なら単独 KO は 0.520、
+-10 秒なら 0.400）。窓を変えた比較で順位相関（5 節）を使うのはこのため。

## 5. GT 検証方法（Q3-B）

### 5.1 GT の作り方

1. 参照窓（±10 秒 = 既定窓）で束ねた**全ストリーク（51 件）が
   `tests/fixtures/highlights_gt/scoring_gt.json` に、裁定前は draft（`tier: null`）
   として入る**。束ね結果は機械生成なので、手で書き写さない
   （`python scripts/highlights_gt_sheets.py --emit-draft`）
2. Idios が各 group の `tier` を **3 = 強 / 2 = 中 / 1 = 弱** で埋める（基準は下記）

**採点はスコアを見ずに行う**（アンカリング回避）。draft にスコア列は無く、
一覧が要るときは `pytest -s tests/test_highlight_scoring_gt.py` の出力（スコアなし）を
使う。スコア付きの一覧は `_worksheet(with_score=True)` でしか出ない。

画像での判定が必要な場合は、各 streak の前後を切り出したコンタクトシートと、
そこで tier を選んで JSON をコピーできるページを生成できる:

```bash
python scripts/highlights_gt_sheets.py \
  --ref-root <ALLAGANEYE_SAMPLE_VIDEO_DIR> \
  --vtuber-root <ALLAGANEYE_SAMPLE_VIDEO_DIR_VTUBER>
# -> output/highlights_gt/index.html (gitignore 済)
```

#### tier の判定基準

「この streak を 1 本のクリップとして投稿するなら出したいか」で判定する。

| tier | 意味 | 目安 |
| --- | --- | --- |
| **3** | 是非出したい | 自分が KO を取った場面を含み、**連続した関与**（KO+KO / KO+ASSIST）でテンポがある。または KO 単独でも決定的な場面 |
| **2** | 他に無ければ出す | KO 単独（普通の 1 対 1）、または **ASSIST 2 件以上**の連続 |
| **1** | 出さない | **ASSIST 単独**、または連続していても実質 1 件分の関与 |

- **KO は ASSIST より上位**（KO 1 件 > ASSIST 2 件、が目安）
- 同 tier 内の優劣は付けない（Spearman は順位のみ見る。迷ったら同じ数字）
- **迷ったら 2**（3 は明確に強い時だけ）
- 見ないもの: 画面の見栄え、動画内の位置、モデルが拾えるかどうか

GT は**参照窓のグループ（イベント列そのもの）を保持**し、時刻だけに依存させない:

```json
{
  "reference_window_seconds": 10.0,
  "provenance": "...",
  "cases": [
    {
      "label": "ref1",
      "source": "tests/fixtures/indicators_gt/20260116_1.json",
      "groups": [
        { "tier": 3, "events": [{ "kind": "ko", "start": 123.4 }, { "kind": "assist", "start": 127.0 }] },
        { "tier": null, "events": [{ "kind": "assist", "start": 200.5 }] }
      ]
    }
  ]
}
```

イベント列を持たせるのは、**窓を変えたときの対応付けを決定的にする**ため。
時刻（丸め値）で突き合わせると、イベント列や束ね規則を変えたときに静かに
別グループと一致しうる。

draft のままでも**構造の検査（5.3 節の 1・2 番目）は有効**になる。`tier` を全部
埋めた時点で Spearman ゲートが有効化される。

### 5.2 窓の感度チェック

参照窓は**下限**として扱う（±10 秒で束ねたグループは、より広い窓では必ず
1 本に収まる）。窓 `W >= reference` について:

1. 各 case のイベントを `W` で束ねる
2. 参照グループを、その全イベントを含む `W` のストリークへ写す
3. `W` のストリークの参照段階 = 写ってきた参照段階の **max**（「その範囲で
   一番良い瞬間」がハイライトの強さだとみなす）
4. 全 case の (モデルスコア, 参照段階) で Spearman 相関 `rho` を取る

`max` を採るのは、ハイライトの体感が「区間の平均」より「最良の瞬間」に
引きずられるため。**ただし広い窓では段階が上方へ寄るバイアスがある**ので、
レポートには `mean` 版の `rho` も併記する（ゲートは `max` 版）。

参照窓の rho がゲート（5.3 節）で、15 / 20 秒は**感度チェック**として表に出すだけ。

### 5.3 合否

1. 参照グループが `group_streaks(events, reference_window)` の結果と**一致**すること
   （GT と実装のドリフト検出。draft でも実行する）
2. GT のイベント集合が indicators の GT と**完全一致**すること（グループの取りこぼし検出）
3. `reference_window_seconds` が既定窓（10 秒）と一致すること
4. 既定窓の rho が **`> 0`**（向きが正しい）かつ **`>= BASELINE_RHO - 0.02`**（回帰検出）

**なぜ絶対値の合格線（当初の rho >= 0.60）をやめたか**: スコアが同点の項目は
どんな並べ替えでも分離できないので、rho には**同点構造で決まる上限**がある。
2026-11-26 の裁定（51 件）での上限は **0.619** で、0.60 は**理論上は可能**な
水準だが、重みを振っても実測は 0.33 までしか上がらない（6.1 節）。
「理論上可能だが、重みでは届かない」閾値をゲートにすると、赤になり続ける
テストを置くことになる。

代替として **実測値を回帰ピンにする**（`BASELINE_RHO = 0.231`）。これは品質の主張
ではなく、「スコア式や束ねを変えたときに相関が悪化したら気づく」ための基準線。
数値そのものの評価は 6 節の表と precision@10 で行う。

### 5.4 GT が未裁定のときの扱い

| 状態 | 挙動 |
| --- | --- |
| `scoring_gt.json` が無い | GT テストは**理由付きで skip**（`#992` の areamap GT と同じ扱い） |
| draft（`tier: null` が残る） | **構造と束ねの整合（5.3 節の 1–3 番目）は実行**し、Spearman だけ skip |
| 裁定済（`tier` が全件埋まる） | 全項目を実行（毎 PR の回帰ゲート） |

Spearman の経路（ロード → 窓写像 → 相関）は、裁定を待たずに**合成 GT** で
検証してある（`test_synthetic_gt_runs_the_full_gate_path`）。合成 GT はスコアから
機械的に tier を作るので精度の根拠にはならないが、写像の取り違えを検出できる。
逆順の合成 GT で `rho < 0` になること（ゲートが実際に落ちること）も pin している。

**このテストは `slow` マーカーを付けない。** 入力は既存の GT JSON
（`tests/fixtures/indicators_gt/*.json`）だけで動画を開かないため、CI の
既定実行に含められる。

## 6. 実測（2026-11-25、GT イベント 87 件 / 3 case）

`tests/fixtures/indicators_gt/*.json` の GT イベント（`20260116_1` 31 件 /
`20260116_5` 51 件 / `other_hud` 5 件）を入力にした束ね結果:

| 窓 | ストリーク数 | 複数イベント | 最大サイズ | サイズ分布 |
| --- | --- | --- | --- | --- |
| ±5 秒 | 63 | 18（29%） | 3 | 1:45 / 2:12 / 3:6 |
| ±10 秒 | 51 | 24（47%） | 5 | 1:27 / 2:15 / 3:7 / 4:1 / 5:1 |
| ±15 秒 | 40 | 19（48%） | 7 | 1:21 / 2:7 / 3:5 / 4:2 / 5:2 / 6:2 / 7:1 |
| ±20 秒 | 33 | 19（58%） | 9 | 1:14 / 2:6 / 3:5 / 4:2 / 5:2 / 6:2 / 7:1 / 9:1 |

**±5 秒では 71% が単独イベントである。** これは spec 5.3 節の既定を否定する材料では
ない（単独 KO にも価値はある）が、窓の既定をどこに置くかには直接効く:

スコアの分布は ±5 秒で **11 種類しかなく、うち 38 件が 0.372（単独 ASSIST）に集中**する:

| 窓 | スコアの異なり数 | 最大の同点塊 |
| --- | --- | --- |
| ±5 秒 | 11 | 38 件（0.372 = 単独 ASSIST） |
| **±10 秒（既定）** | **25** | **21 件（0.252 = 単独 ASSIST）** |
| ±15 秒 | 21 | 15 件 |
| ±20 秒 | 21 | 9 件 |

> **帰結**: ±5 秒の Spearman は 27 件の同点塊に支配され、**識別力がほぼ無い**。
> これが既定窓を ±10 秒にした根拠（1.1 節）。GT 裁定は ±10 秒の 51 件に付け、
> ±15 / ±20 秒は感度チェックとして rho を併記する。

### 6.1 人手裁定の結果（2026-11-26、51 件）

`ref` は ±10 秒の 51 グループに対する裁定で、**31 件 = 3 / 20 件 = 2**
（tier 1 は未使用）。GT テストが出力する表:

| 窓 | n | rho | 上限 rho | precision@10 | 母集団の 3 の割合 |
| --- | --- | --- | --- | --- | --- |
| **10 秒（既定）** | 51 | **+0.231** | 0.619 | 0.70 | 0.61 |
| 15 秒 | 40 | +0.357 | 0.684 | 0.70 | 0.62 |
| 20 秒 | 33 | +0.273 | 0.704 | 0.70 | 0.67 |

「上限 rho」は**同点グループの並び順だけを最良に選べる**としたときの値（各グループの
平均 tier 順位で並べた場合）。グループ内で段階が割れている分だけ 1.0 から下がる。

**読み方**:

- 既定窓の rho は弱い。ただ、これは**重みの問題ではない**: `assist_weight` を 0→1.5、
  `length_share` を 0→1 まで振っても rho は 0.20〜0.33 の範囲を出ない
- **上限が 0.619 までしかない**。原因はスコアの粒度で、±10 秒では 51 件が 25 種類の
  スコアにしかならず、特に**単独 ASSIST 21 件が完全に同一**（0.252）になる。
  人手はそれらを 3 / 2 に分けているので、**現信号（KO / ASSIST の発生時刻）には
  入っていない情報を人が見ている**。この 21 件だけで上限が 0.619 まで下がる
- precision@10 = 0.70 は母集団 0.61 に対して +9 pt。上位だけを取る用途では
  「ランダムより少しマシ」程度
- 窓を広げると rho は 0.357 まで上がる（束ね直しで同点塊が崩れるため）。
  ただし既定は ±10 秒（1.1 節）で、15 秒は参考値

**したがって、「rule-based スコアリングが GT 検証されている」の内容は**
「人手の順位に対して**正の相関があることを測定し、上限と限界を記録した**」で
あって、「人手の順位を再現できる」ではない。

## 7. 未決事項

1. **`assist_weight` / `saturation` / `full_density` / `length_share`**:
   現値は「単独 KO > 単独 ASSIST かつ KO+ASSIST が単独 KO より上」という順序制約
   だけを満たす初期値。**重みの振り幅では rho は改善しないことが実測で分かった**
   ので、重みの再調整は優先度低（信号追加の方が効く）
2. **信号追加 / ML 導入判断**（issue 作業項目 4）: 6.1 節の「単独 ASSIST 21 件を
   区別できない」が根拠。位置・キルログ・ダメージ等の信号を足さない限り、
   人手の順位には近づかない見込み。0.4.0 では実施しない
3. **tier 1 が未使用**: 裁定で 1 が 1 件も出ず、GT が 2 値になっている。
   これは「出さないクリップ」を選ばなかったという判断であり、GT としては
   識別力が低い側に倒れる。再裁定するかは 0.4.0 以降の判断

## 8. 実装メモ

- 公開 API: `group_streaks` / `score_streak` / `score_events` / `rank_streaks` /
  `to_highlights` / `scoring_events_from_metadata`
- `DEFAULT_WINDOW_SECONDS = 10.0`。窓を変えるときはこの定数か
  `window_seconds=` 引数。CLI / GUI からの指定は L7 (#135) で公開する
- `score_events` は**発生時刻昇順**を返す（`rank_streaks` は別関数）。並びを
  暗黙に変えると `event_positions` の対応が読み手から追えなくなるため分けた
- `to_highlights` の `index` は**スコア順の 1 始まり**。`event_positions` は
  metadata `events[]` の 1 始まり索引で、L7 が前後秒数拡張に使う
- `Highlight.start` / `end` は**イベントの活動区間**（最初の発生〜最後の終了）。
  `--pre` / `--post` の拡張は L7 の責務
- `metadata.highlights[]` の write-back・schema 追加は #135（L7）。本 phase は
  `to_payload()` の形までを固定する
